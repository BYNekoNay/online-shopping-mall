# 数据库规范

> **版本状态**：v0.1 规划版，基于毕业设计任务书编制，尚未与实际代码核对，详见 `00-文档说明.md`。
>
> **本文档定位**：`05-详细设计说明书.md` §2 给出的是表的用途与关键字段说明；本文档给出可直接执行的 DDL 级正式规范，是数据库建表脚本（`08-开发指南.md` §2.4 所述 `src/main/resources/sql/`）的直接来源。开发中表结构如需调整，**先修改本文档，再改建表脚本**，与 `09-接口规范.md` 保持一致的"先文档后实现"纪律。

## 1. 通用规范

### 1.1 基础约定

- 存储引擎：InnoDB；字符集：`utf8mb4`；排序规则：`utf8mb4_general_ci`；
- 表名/字段名：小写下划线命名（snake_case），单数形式（如 `product` 而非 `products`）；
- 主键：`id BIGINT UNSIGNED AUTO_INCREMENT`，命名固定为 `id`；
- 通用字段：除特别说明外，各表均包含 `create_time`（`DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`）、`update_time`（`DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`）；用户可直接删除的业务主表另包含 `is_deleted`（`TINYINT(1) NOT NULL DEFAULT 0`，逻辑删除标记，MyBatis-Plus 自动拼接 `is_deleted = 0` 条件）；日志/明细类只增不改的表（如 `order_item`、`operation_log`、`page_view_log`）不设 `is_deleted`；
- 金额字段：统一 `DECIMAL(10,2)`，禁止使用浮点类型；
- 状态类字段：统一 `TINYINT`，具体枚举值在字段注释中说明，不额外建状态字典表（除非枚举值需要运营人员动态维护，如物流公司列表走 `dict` 表）；
- JSON 结构字段：MySQL 8.0 优先使用原生 `JSON` 类型（自动校验合法性）；仅当字段需要参与老版本兼容或简单展示时使用 `TEXT`/`VARCHAR` 存 JSON 字符串。

### 1.2 外键与索引策略

- **不使用物理外键约束**（`FOREIGN KEY`），关联关系由应用层保证，原因：避免级联删除/更新引发的意外数据丢失，减少高并发写入时的锁竞争，便于后续分库分表；
- 所有作为关联查询条件的字段（如 `user_id`、`product_id`、`shop_id`、`order_id`）**必须建立普通索引**；
- 业务上要求唯一的字段（如 `user.username`、`order.order_no`）建立唯一索引；
- 高频组合查询条件建立复合索引（如 `user_behavior(user_id, product_id, behavior_type)`），复合索引字段顺序遵循"等值查询字段在前、范围查询字段在后"的最左前缀原则；
- 避免为区分度极低的字段（如 `is_deleted`、单独的 `status`）单独建索引，通常与其他字段组成复合索引使用。

### 1.3 命名冲突提示

`order` 为 MySQL/SQL 保留字，本规范文档中沿用 `05-详细设计说明书.md` 已使用的逻辑表名 `order` 以保持文档一致性，DDL 中一律使用反引号转义；**实际建表脚本中建议直接使用物理表名 `orders`**，避免每次手写 SQL 都要转义保留字，实现时只需在此处与代码之间做一次命名映射，不影响本规范中其余章节对"订单表"的引用。

#### 2.4.1 `coupon.discount_rule` JSON 结构

`discount_rule` 固定为以下二选一结构，字段 `mode` 区分具体计算方式，与 `coupon.type`（新人/满减/品类/店铺，描述的是券的**归属与发放对象**）正交——同一 `type` 的券可以是满减也可以是折扣：

```json
// mode=REDUCE（满减）
{ "mode": "REDUCE", "threshold": 99.00, "reduceAmount": 10.00 }

// mode=DISCOUNT（满折）
{ "mode": "DISCOUNT", "threshold": 99.00, "discountPercent": 0.9 }

// coupon.type=3（品类券）时额外携带 categoryId 字段，与上述 mode 结构叠加：
{ "mode": "REDUCE", "threshold": 99.00, "reduceAmount": 10.00, "categoryId": 12 }
```

- `threshold`：订单商品金额（不含运费）达到该值才可使用，`0` 表示无门槛（新人券常见配置）；
- `mode=REDUCE` 时 `reduceAmount` 为直接抵扣金额；`mode=DISCOUNT` 时 `discountPercent` 为折扣率（`0.9` 表示9折，即 `discountAmount = goodsAmount * (1 - discountPercent)`）；
- 计算得到的 `discountAmount` 不得超过订单商品金额本身（折扣券在极小订单金额时可能计算出接近全免的抵扣，需在 `CouponService` 中做 `Math.min(discountAmount, goodsAmount)` 兜底）；
- `categoryId`：仅 `coupon.type=3`（品类券）时存在于 `discount_rule` 中（`coupon` 表本身不单独建 `category_id` 列，避免为一种券类型单独加一列——该字段直接内嵌进本就是 JSON 的 `discount_rule`）；使用校验时要求**该分组订单中至少有一件商品的 `product.category_id = categoryId`** 才允许使用该券（不满足抛 `40003` 优惠券不可用），校验通过后 `threshold`/`discountAmount` 仍按整个分组订单商品金额计算（不单独拆分出该分类下商品的子金额计算折扣），保持与满减券/店铺券一致的简单计算方式，避免引入"部分商品参与折扣"的复杂拆分逻辑；
- `coupon.type=1`（新人券）**不额外校验"用户是否为新用户/是否首次下单"**——"新人券"仅是运营侧对该优惠券的命名与投放场景（如注册后自动发放，发放逻辑不在本项目范畴内），其领取/使用校验与 `type=2`（满减券）完全一致（有效期+库存+门槛），二者仅 `type` 取值不同、不存在额外的资格限制字段或逻辑，避免为区分二者引入"用户历史订单数查询"这类超出毕业设计范畴的额外校验。

#### 2.4.2 `promotion.rule_json` JSON 结构（按 `type` 区分）

```json
// type=1 限时折扣：scope/scope_id指定的商品/分类/店铺在活动期间按折扣率售卖
{ "discountPercent": 0.8 }

// type=2 满减：支持多档满减（金额越高档位优先匹配最高档）
{ "tiers": [ { "threshold": 100.00, "reduceAmount": 10.00 }, { "threshold": 200.00, "reduceAmount": 25.00 } ] }

// type=3 满赠：达到门槛赠送指定商品（赠品不占用赠品本身库存以外的资源，随订单一并出库）
{ "threshold": 150.00, "giftProductId": 5001, "giftSkuId": 50011, "giftQuantity": 1 }

// type=4 组合套餐：多个商品组合以固定总价售卖，purchase时按productIds原价占比拆分到各order_item
{ "productIds": [1001, 1002, 1003], "bundlePrice": 99.00 }
```

- `scope`/`scope_id` 决定该促销规则适用的商品范围（`PRODUCT`→单个商品，`CATEGORY`→整个分类，`SHOP`→整个店铺），`type=4`（组合套餐）例外——其适用商品固定为 `rule_json.productIds` 列出的商品集合，此时 `scope` 固定填 `PRODUCT`、`scope_id` 可为空（不使用该字段判断范围，仅用 `rule_json.productIds`）；`rule_json.productIds` 中的商品必须同属一个 `shop_id`（管理员配置时校验，不满足拒绝保存），因为下单时按 `shop_id` 分组在先（`11-后端开发详细文档.md` §4.1 步骤2），组合套餐的匹配只在同一分组内部判断"是否完整覆盖"，跨店铺的商品组合天然无法在一次子订单内凑齐；
- 同一商品若命中多个生效中的促销/优惠券，`PromotionService`/`CouponService` 的抵扣叠加规则：**促销（满减/折扣）与优惠券可叠加，但同类型的多个促销之间取抵扣金额最大的一个生效**（不允许同类型促销与自身叠加），避免营销规则组合爆炸超出毕业设计范畴；叠加计算顺序固定为**先促销后优惠券**——`type=1`/`type=4` 直接改变 `order_item.price` 单价快照，`type=2` 产出独立的 `promotionDiscountAmount`，优惠券的门槛判断与 `couponDiscountAmount` 计算均基于促销调整后的商品金额（下单流程实现步骤见 `11-后端开发详细文档.md` §4.1）；
- `type=3`（满赠）不产生金额抵扣，而是在下单时额外插入一条 `order_item.is_gift=1`、`price=0` 的赠品行（赠品同样需要 `StockService` 预扣减库存，库存不足时静默跳过赠送、不阻断本次下单）；赠品行不可单独发起售后（仅随整单退款/退货一并处理，因其本身无退款金额），商家/平台销售统计（`11-后端开发详细文档.md` §8）按 `is_gift=0` 过滤，避免赠品拉高销量/GMV统计口径；`giftSkuId` 必填且必须精确指定 `product` 表 `sku` 下的某一具体 SKU（即使赠品商品仅有单一规格也需指定该唯一 SKU 的 `id`），管理员配置满赠活动时由后台表单选择赠品商品后联动加载其 `skuList` 供二次选择，避免赠品商品存在多规格时系统无法判断赠送哪一规格。

#### 2.4.3 积分规则（固定比例，避免引入运营可配置的复杂度）

| 场景 | 规则 |
|---|---|
| 下单获取（`type=1`） | 订单**实付金额**每 1 元获得 1 积分，支付成功后（`11-后端开发详细文档.md` §4.4 支付回调流程第4步）写入正记录并累加 `user.points`；**获取记录自动带 365 天 `expire_time`（C-2）** |
| 订单抵扣（`type=2`） | 100 积分抵扣 1 元，抵扣金额不得超过订单商品金额的 50%（`discountAmount = min(pointsUsed / 100, goodsAmount * 0.5)`），下单时若传入 `usePoints` 则在 `OrderService.createOrder` 中一并写入负记录并扣减 `user.points`（与优惠券抵扣可叠加，最终 `discountAmount` 为优惠券抵扣+积分抵扣之和，但整体不超过商品金额） |
| 兑换（`type=3`） | 预留枚举（本项目积分商城兑换使用 `type=5` 记录，见下） |
| 积分商城兑换（`type=5`，C-1） | 用户在积分商城兑换商品时写入负记录（`change_amount=-cost`），同步插入 `points_exchange_log` 快照；兑换流程：原子扣库存 → 原子扣积分（`points>=cost`）→ 积分不足回滚库存 |
| 取消/退款返还（`type=4`） | 订单退款时，若该订单曾产生下单获取的积分且尚未被消耗，需扣回对应积分（写入新的负记录，`related_order_id` 指向原订单）；若涉及积分已被后续订单消耗，允许 `user.points` 扣为负数上限为0（即最多扣至0，不出现负余额） |
| 积分过期（C-2） | 每日 03:00 定时任务清理已过期（`expire_time < now` 且 `expired=0`）的获取记录：按用户汇总过期量从 `user.points` 扣减（`GREATEST(...,0)` 防负），随后标记 `expired=1`（幂等，防重复清理清掉新积分）；简化 FIFO，毕设场景近似实现 |

## 4. 数据库脚本管理规范

- 脚本目录：`src/main/resources/sql/`（见 `08-开发指南.md` §2.4）；
- 版本化命名：采用类似 Flyway 的编号方式，如 `V1__init_schema.sql`（初始建表）、`V2__add_freight_template.sql`（新增运费模板表）、`R__seed_dict_data.sql`（可重复执行的基础数据脚本，前缀 `R__`）；
- 已提交并在其他环境执行过的脚本不得直接修改，表结构变更一律新增下一版本号脚本，保证任意环境按顺序执行脚本都能得到一致的库结构；
- 初始化数据（管理员账号、根分类、物流公司字典等）与建表脚本分离，放入 `R__seed_data.sql`，便于开发/测试环境重复导入而不冲突。
