> **版本状态**：v0.1 规划版，基于毕业设计任务书编制，尚未与实际代码核对，详见 `00-文档说明.md`。

> **本文档定位**：`08-开发指南.md` §2 给出的是后端工程的总体结构、分层职责与开发顺序；本文档在其基础上进一步下钻到**每个模块的类结构、关键方法、具体实现步骤**，是编码阶段可以直接对照的实现细则。接口字段以 `09-接口规范.md` 为准，数据库字段以 `10-数据库规范.md` 为准，推荐算法的深入设计见 `12-核心算法设计文档.md`（本文档仅从工程实现角度描述推荐模块如何接入，不重复算法本身）。

## 1. 基础设施模块详细设计

基础设施先于所有业务模块开发（对应 `08-开发指南.md` §1.2 顺序0），后续模块直接复用，不再各自实现一套。

### 1.1 统一响应结构

```java
// common/Result.java
public class Result<T> {
    private int code;
    private String message;
    private T data;

    public static <T> Result<T> success(T data) { ... }   // code=0
    public static <T> Result<T> success() { ... }          // data=null
    public static <T> Result<T> error(ErrorCode errorCode) { ... }
    public static <T> Result<T> error(int code, String message) { ... }
}
```

- `ErrorCode` 为枚举，字段 `code`/`message`，取值按 `09-接口规范.md` §4 错误码表分段维护，新增错误码时同时更新该文档与此枚举，避免二者漂移；
- 分页统一包装 `PageResult<T>{ total, pageNum, pageSize, pages, records }`，对应 MyBatis-Plus `Page<T>` 转换而来的工具方法 `PageResult.of(Page<T> page)`。

### 1.2 异常体系与全局异常处理

```
common/exception/
├── BusinessException.java   # 业务异常，构造函数传入 ErrorCode，携带自定义提示
├── GlobalExceptionHandler.java  # @RestControllerAdvice
```

`GlobalExceptionHandler` 捕获顺序（由具体到泛化）：

1. `BusinessException` → 直接取其 `ErrorCode` 包装为 `Result.error(...)`；
2. `MethodArgumentNotValidException`（`@Valid` 校验失败）→ 提取第一条校验错误信息，返回 `10001` 参数校验失败；
3. `Exception`（兜底未知异常）→ 记录 `ERROR` 级别日志（含堆栈），返回 `10005` 系统繁忙，**不将异常堆栈暴露给前端**。

### 1.3 JWT 鉴权

```
security/
├── JwtUtil.java          # generateToken(userId, role) / parseToken(token) / isExpired(token)
├── JwtInterceptor.java    # HandlerInterceptor，解析请求头Authorization，写入ThreadLocal
├── LoginUserContext.java  # ThreadLocal持有当前登录用户{userId, role}，提供静态方法getCurrentUserId()
├── RequireRole.java       # 自定义注解 @RequireRole({2}) 标注在Controller方法上，声明允许的角色
├── RoleCheckAspect.java   # AOP切面，读取RequireRole注解值与LoginUserContext中的角色比对，不符抛403
```

- `JwtInterceptor` 在 `WebMvcConfigurer` 中注册，`excludePathPatterns` 排除 `09-接口规范.md` 标注为"公开"的接口（登录、注册、商品浏览类只读接口、`GET /api/recommend/guess-you-like`、`GET /api/recommend/similar/{productId}`）——这些路径**不会因缺少/失效 Token 而被拦截器拒绝**；
- **白名单路径的"可选登录"处理**：`JwtInterceptor` 对白名单路径仍尝试解析 `Authorization` 头（如果存在），解析成功则照常写入 `LoginUserContext`（供 Controller 内部区分登录态使用，如 `guess-you-like` 依此判断是否有 `userId` 可用于个性化推荐）；解析失败或未携带 Token 时，**不抛出401，直接放行**，`LoginUserContext.getCurrentUserId()` 返回 `null`，业务代码按 `12-核心算法设计文档.md` §8 冷启动逻辑走热门兜底；
- 非白名单路径：Token 校验失败（过期/签名错误/缺失）→ 拦截器直接返回 `401`，不进入 Controller；
- `LoginUserContext` 必须在请求结束时清理 ThreadLocal（拦截器 `afterCompletion` 中 `remove()`），避免线程池复用导致的用户信息串用。

### 1.4 跨域与 Redis 配置

- `CorsConfig`：开发环境放通本地前端开发服务器端口；生产环境改为经 Nginx 反向代理同源，无需 CORS（见 `08-开发指南.md` §4.2）；
- `RedisConfig`：`RedisTemplate<String, Object>` 的 key 用 `StringRedisSerializer`，value 用 `Jackson2JsonRedisSerializer`，避免默认 JDK 序列化产生的可读性差、体积大的问题；
- Redis key 命名统一加模块前缀，避免不同模块 key 冲突：`stock:{skuId}`（库存，**永不设置 TTL**，见 §4.2 说明）、`lock:stock:{skuId}`（分布式锁，`leaseTime` 见 §4.2）、`recommend:{userId}`（推荐结果缓存，TTL 随定时刷新周期设置，如24小时）、`hot:products`（热门商品兜底缓存，TTL 随定时刷新周期设置）。

### 1.5 MyBatis-Plus 配置

- 分页插件 `PaginationInnerInterceptor`：全局分页，Controller/Service 层统一使用 `Page<T>` 对象，禁止手写 `LIMIT` 拼接；
- 自动填充 `MetaObjectHandler`：`insert` 时自动填充 `createTime`/`updateTime`，`update` 时自动填充 `updateTime`，避免每个 Service 手动 `set` 时间字段；
- 逻辑删除：全局配置 `is-deleted` 字段名与取值（`0`/`1`），删除操作统一走 `removeById`/`remove(wrapper)`，不手写 `UPDATE ... SET is_deleted=1`。

**注册流程**（`UserServiceImpl.register`）：
1. 校验 `username` 是否已存在（`UserMapper.selectCount` 按 `username` 查询，非 0 抛 `20003`）；
2. `BCryptPasswordEncoder.encode(password)` 加密后写入 `User.password`；
3. 插入并返回 `userId`。

**登录流程**（`UserServiceImpl.login`）：
1. 按 `username` 查询用户，不存在或 `BCryptPasswordEncoder.matches` 失败 → 抛 `20001`；
2. 校验 `status`，禁用抛 `20002`；
3. `JwtUtil.generateToken(user.id, user.role)` 生成 Token，返回 `LoginVO{ token, userId, role, nickname }`。

地址管理（`address` 表）复用同一 Controller 的 `/api/user/addresses` 子路径，Service 内校验 `userId` 归属，防止越权访问他人地址。

### 2.1 商家入驻与店铺模块（`modules/shop/`）

```
modules/shop/
├── controller/ShopController.java     # /api/merchant/shop/**（商家端）
├── service/ShopService.java / impl/ShopServiceImpl.java
├── mapper/ShopMapper.java
├── entity/Shop.java
├── dto/ShopApplyDTO.java, ShopUpdateDTO.java
├── vo/ShopVO.java, ShopApplyStatusVO.java
```

管理员端的 `AdminShopController.java`（见 `9. 管理员模块`）与本模块共用 `ShopService`/`ShopMapper`/`Shop` 实体，不重复建表/建 Mapper；`AdminShopController` 仅承担审核动作（调用 `ShopService.audit(shopId, approved, reason)`），店铺记录的增删改查逻辑统一在 `ShopService` 中实现。

**入驻申请流程**（`ShopServiceImpl.apply`，对应 `09-接口规范.md` §2.5 `POST /api/merchant/shop/apply`）：
1. 按 `merchantUserId`（即 `LoginUserContext.getCurrentUserId()`）查询 `shop` 表是否已有记录；
2. 若已存在且 `status ∈ {0待审核, 1正常, 3已禁用}`，抛 `10001` 参数校验失败（提示"已有申请记录/已入驻"，与 `shop.merchant_user_id` 唯一索引保持一致，避免并发重复提交撞唯一键异常直接抛 500）；
3. 若不存在，或已存在且 `status=2`（已拒绝，允许重新提交）→ 插入（不存在时）或更新（已拒绝重新提交时复用同一条记录，同时清空 `reject_reason`）：`status` 固定写为 `0`，写入 `name`/`contactName`/`contactPhone`/`licenseNo`/`licenseImage`/`applyReason`；
4. 返回 `{ shopId, status: 0 }`。

**申请状态查询**（`ShopServiceImpl.applyStatus`，对应 `GET /api/merchant/shop/apply-status`）：按 `merchantUserId` 查询 `shop` 表，无记录返回 `{ hasApplied: false }`，有记录返回 `{ hasApplied: true, shopId, status, rejectReason }`。

**店铺信息获取/更新**（`ShopServiceImpl.getInfo`/`updateInfo`，对应 `GET/PUT /api/merchant/shop`）：先按 `merchantUserId` 查询 `shop` 记录且校验 `status=1`，不满足（无记录或未通过审核）统一抛 `10004` 资源不存在；`updateInfo` 仅允许更新 `name`/`logo`/`description`/`decorationConfig`，不允许通过该接口修改 `status`/入驻申请字段。

**审核动作**（`ShopServiceImpl.audit`，由 `AdminShopController.auditShop` 调用，对应 `PUT /api/admin/shops/{id}/audit`）：`approved=true` 时 `status` 置为 `1` 并清空 `reject_reason`；`approved=false` 时 `status` 置为 `2` 并写入 `reject_reason`（取请求体 `reason` 字段）。

商品/订单等其余商家接口在 Service 层统一通过 `ShopService.getMerchantShopIdOrThrow(merchantUserId)`（内部校验 `status=1`，不满足抛 `10004`）获取当前商家的 `shopId`，不在各业务 Controller 中重复实现该校验逻辑。

### 4.1 下单流程实现步骤（对应 `05-详细设计说明书.md` §4.1）

`OrderService.createOrder(CreateOrderDTO dto)`：**返回值为订单列表**，因为跨店铺下单需按 `shop_id` 拆分为多个订单（对应 `05-详细设计说明书.md` §2.2、`09-接口规范.md` §2.4 的数组响应）：

1. 参数与幂等校验：按 `requestId`（见 `09-接口规范.md` §1.5）查 Redis，命中则直接返回缓存的下单结果（整个订单数组），不重复执行；
2. 组装商品明细并按 `shop_id` 分组：从购物车（`cartItemIds`）或直接商品（`productItems`）读取商品/SKU 当前价格、名称、主图（连同 `shopId`）作为快照，按 `shopId` 分组得到多个"待创建订单组"，**后续第3-7步对每个分组独立执行**（分组间互不影响，某一分组失败不影响其他分组已创建的订单，见下文步骤8）；
3. 对每个分组：计算运费——调用 `FreightService.calculate(shopId, addressId, goodsAmount)`，按 `freight_template.region_rule_json` 匹配收货地址所在区域（区域匹配规则与省份映射表见 `10-数据库规范.md` §2.2 `freight_template` 表说明），命中包邮门槛返回 0，未配置模板的店铺走平台默认运费（对应 FR-X-08）；
4. 计算促销优惠：对分组内每个商品调用 `PromotionService.matchActive(scope, scopeId)` 匹配当前生效促销（同一商品命中多个同类型促销时取抵扣金额最大的一个，见 `10-数据库规范.md` §2.4.2）——`type=1`限时折扣：按 `discountPercent` 折算该商品单价，`order_item.price` 直接记录折后单价（`goodsAmount` 按折后单价汇总）；`type=2`满减：按分组商品原价小计匹配 `tiers` 最高档得到独立的 `promotionDiscountAmount`；`type=3`满赠：分组商品小计达到 `threshold` 时标记该分组"待附赠 `giftProductId`/`giftSkuId`/`giftQuantity`"，供步骤5/6处理，赠品不产生金额抵扣；`type=4`组合套餐：分组内购买商品若完整覆盖 `rule_json.productIds`（每个商品数量均≥1）则按各商品原价占比将 `bundlePrice` 拆分为各自的 `order_item.price`，未完整覆盖时各商品按原价/其他命中促销正常计算；
5. 计算优惠券抵扣（如传入 `couponId`）：校验优惠券归属（`coupon.shop_id` 为空表示平台券可用于任意分组，否则仅能用于 `shop_id` 匹配的分组）与有效期/门槛，基于**步骤4促销调整后的商品金额**计算该分组的 `couponDiscountAmount`（对应 `10-数据库规范.md` §2.4.2 "先促销后优惠券"的叠加顺序）；若传入 `usePoints=true`，**仅对分组数组中第一个分组**额外调用 `PointsService.calculateDeduct(userId, goodsAmount)` 计算积分抵扣额度 `pointsDeductAmount`（对应 `09-接口规范.md` §2.4 "积分只抵扣第一笔子订单"的约定，避免同一笔积分被多个分组重复计算），其余分组固定 `pointsDeductAmount=0`；
6. 调用 `StockService.deduct(skuId, quantity)` 执行 Redis 分布式锁 + 库存预扣减（见 4.2 节）——**按分组独立执行**，范围含步骤4标记的赠品 SKU：同一分组内某个正常购买 SKU 预扣减失败时，**该分组内此前已扣减成功的其他 SKU 需立即调用 `StockService.rollback` 归还**（分组内保持"要么全部扣减成功、要么全部归还"），但不影响其他分组；已成功创建的分组（含已扣减的库存）不因其他分组失败而回滚；**赠品 SKU 预扣减失败（库存不足）时不影响本次下单，仅跳过该赠品的附赠**（不触发本条的"全部归还"逻辑，也不计入下单失败判定）；
7. 事务内（`@Transactional`，**每个分组一个独立事务**）：插入该分组的 `order`（`shop_id` 为该分组店铺，`pay_amount = goodsAmount + freightAmount - promotionDiscountAmount - couponDiscountAmount - pointsDeductAmount`，`goodsAmount` 为步骤4促销单价折算/套餐拆分后的商品小计）、批量插入 `order_item`（含步骤4/6成功附赠的赠品行，`is_gift=1`、`price=0`）、标记该分组使用的优惠券为已使用；若该分组 `pointsDeductAmount > 0`，调用 `PointsService.settleDeduct(userId, pointsUsed, orderId)` 写入积分负记录并扣减 `user.points`（下单获取的积分正记录延后到支付成功后写入，见 4.4 节第4步，避免"下单未支付即先加积分"）；**Redis 库存操作不纳入该数据库事务**，因为二者是不同的资源，事务提交前如失败需在 `catch` 块中显式调用库存归还，保证最终一致；
8. 汇总所有分组的创建结果：成功创建的分组组成响应数组；某一分组因库存不足等原因创建失败时，**已成功创建的其余分组订单不回滚**，失败分组直接从响应数组中省略（前端据此判断"部分商品下单失败"，见 `09-接口规范.md` §2.4）；
9. 将 `requestId → 下单结果（订单数组）` 写入 Redis 并设置较短过期时间（如10分钟），用于幂等去重；
10. 返回订单数组，每项 `{ orderId, orderNo, shopId, payAmount, freightAmount, promotionDiscountAmount, couponDiscountAmount, pointsDeductAmount }`。

### 4.2 库存预扣减与分布式锁

`StockService`：

```java
public boolean deduct(Long skuId, int quantity) {
    String lockKey = "lock:stock:" + skuId;
    RLock lock = redissonClient.getLock(lockKey);
    if (!lock.tryLock(waitTime, leaseTime, TimeUnit.MILLISECONDS)) {
        throw new BusinessException(ErrorCode.SYSTEM_BUSY);
    }
    try {
        String stockKey = "stock:" + skuId;
        // Redis中无该key时先从数据库加载并写入（懒加载，加锁范围内避免重复加载）
        Long stock = ensureStockLoaded(stockKey, skuId);
        if (stock < quantity) return false;
        redisTemplate.opsForValue().decrement(stockKey, quantity);
        return true;
    } finally {
        lock.unlock();
    }
}

public void rollback(Long skuId, int quantity) {
    redisTemplate.opsForValue().increment("stock:" + skuId, quantity);
}
```

- 锁的 `leaseTime` 需覆盖预扣减逻辑的最长执行时间，避免业务未执行完锁提前释放导致的超卖；优先使用 Redisson 的看门狗机制（不指定 `leaseTime` 时自动续期）而非手工估算固定值，配置项 `mall.stock.lock-wait-seconds`/`lock-lease-seconds` 见 `14-项目脚手架与环境规范.md` §3；
- 支付成功后对数据库 `sku`/`product` 表执行真实库存扣减（`UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?`，利用 `WHERE` 条件而非应用层判断兜底防止并发超卖），并 `sales + 1`；
- 订单超时取消或主动取消时调用 `rollback` 归还 Redis 预扣减库存。

**`stock:{skuId}` 的 TTL 策略（不设置过期时间）**：该 key 代表"当前可售库存"（已扣除所有待付款订单占用的数量），与数据库 `sku.stock`（仅在支付成功时才真正扣减）是两个语义不同的计数——`ensureStockLoaded` 仅在 key **首次不存在**时从数据库懒加载并写入（写入时不设置 `expire`，永久有效直到进程重启或 Redis 数据丢失），之后的每一次扣减/归还都通过 `decrement`/`increment` 原地修改，不再回源数据库覆盖：
- 若给该 key 设置 TTL 并让其自然过期，过期后下一次 `ensureStockLoaded` 会重新从数据库 `sku.stock` 加载——但此时数据库里的 `stock` 尚未扣除那些"已预扣减但未支付"的订单占用数量，等于把已被占用的库存重新"放出来"，造成超卖，因此**禁止**给 `stock:{skuId}` 设置 TTL；
- 已知遗留风险（毕业设计范畴内可接受，不做额外工程化处理）：若 Redis 服务重启或该 key 被意外清空（非正常业务路径导致），下一次访问会重新从数据库加载"未预扣减"的库存值，此时若存在尚未超时取消的待付款订单，其已占用的库存会被重新计入可售数量，短时间内(直至这些订单超时自动取消或支付完成) 存在超卖窗口；生产级方案应在启动时按"数据库库存 − 待付款订单占用量"重建该 key，但该重建逻辑超出本项目范畴，此处仅作为已知限制记录，不在代码中实现。

### 4.3 订单号生成

`OrderNoGenerator`：`yyyyMMddHHmmss` 时间戳 + 4-6位随机数/自增序列，保证同一毫秒内并发下单也不重复（如 `20260706153000` + 6位 Redis `INCR` 生成的序列号取模）。不引入雪花算法等重量级方案，量级足够。

### 4.4 支付回调

`OrderService.handlePayCallback`：

1. 校验 `payNo` 对应支付记录是否已处理（`status != 0`），已处理直接返回成功（幂等）；
2. 更新 `payment.status`、`order.status`（待付款→待发货）、`order.pay_time`；
3. 调用 4.2 节"支付成功后"的真实库存扣减；
4. 调用 `PointsService.settleEarn(orderId, userId, payAmount)` 按实付金额 1:1 写入积分正记录并累加 `user.points`（对应 `10-数据库规范.md` §2.4.3 "下单获取"规则；此步骤在支付成功后才执行，与第7步下单时已写入的积分抵扣负记录是两条独立流水，不互相影响）。

### 4.5 订单超时自动取消

```java
@Scheduled(cron = "0 * * * * ?")  // 每分钟
public void cancelTimeoutOrders() {
    List<Order> timeoutOrders = orderMapper.selectTimeoutUnpaidOrders(timeoutMinutes);
    for (Order order : timeoutOrders) {
        orderService.cancelOrder(order.getId(), CancelReason.TIMEOUT);
    }
}
```

`selectTimeoutUnpaidOrders` 利用 `10-数据库规范.md` 中 `order` 表的复合索引 `idx_status_create_time` 避免全表扫描。`cancelOrder` 内部统一调用库存归还与优惠券释放逻辑，与用户主动取消订单复用同一方法，避免两套取消逻辑分叉导致遗漏归还步骤。

### 4.6 退款/退货

`RefundService`：消费者发起 → 商家审核（`PUT /api/merchant/refunds/{id}/audit`）→ 审核通过按"仅退款"直接调支付模块退款，按"退货退款"等待商家确认收货后再退款并调用 `StockService` 恢复真实库存（不经过 Redis 预扣减路径，因为发货后库存已是真实扣减状态）；退款生效时调用 `PointsService.clawback(orderId)` 扣回该订单曾获取的积分（见 §7 `PointsService.clawback` 说明）；`orderItemId` 指定为具体明细行发起售后时，`order_item.is_gift=1` 的赠品行不允许作为 `orderItemId` 单独发起（`refund.amount` 按其 `price=0` 计算恒为0，无实际退款意义，前端不对赠品行展示"申请售后"入口，见 `13-前端开发详细文档.md` §2.6），赠品仅随其所属订单的整单退款/退货一并处理（不单独退回赠品库存，只在退货退款场景下随整单一起走 `StockService` 库存恢复）。

## 7. 营销与物流模块

```
modules/marketing/
├── controller/CouponController.java, PromotionController.java
├── service/CouponService.java, PromotionService.java, PointsService.java

modules/logistics/
├── controller/FreightTemplateController.java, LogisticsController.java
├── service/FreightService.java, LogisticsQueryService.java
```

- `CouponController`/`PromotionController` 同时承载消费者端只读路径（`/api/coupons/**`、`/api/user/coupons`、`/api/promotions/active`）与管理员端管理路径（`/api/admin/coupons/**`、`/api/admin/promotions/**`，方法上 `@RequireRole({3})`），不额外拆分 `AdminCouponController`——两类路径共用同一套 `CouponService`/`PromotionService`，仅 Controller 层按角色注解区分可访问性；
- `CouponService.receive`：校验 `coupon.valid_to` 未过期、`received_count < stock`（`UPDATE coupon SET received_count = received_count + 1 WHERE id=? AND received_count < stock` 借乐观更新防超发，影响行数为0时抛 `60001`），写入 `user_coupon` 记录；`type=1`（新人券）与 `type=2`（满减券）走完全相同的领取/使用校验逻辑，不额外查询用户历史订单（见 `10-数据库规范.md` §2.4.1 关于"新人券"命名的说明）；
- `CouponService.calculateDiscount(order, couponId)`：按 `10-数据库规范.md` §2.4.1 的 `mode` 分支计算抵扣金额，`Math.min(discountAmount, goodsAmount)` 兜底；`coupon.type=3`（品类券）额外校验该分组订单的 `order_item` 中至少存在一条 `product.category_id = discountRule.categoryId` 的记录，不满足抛 `40003`（校验通过后仍按整组订单金额计算抵扣，不单独拆分品类子金额，见 `10-数据库规范.md` §2.4.1 说明）；本方法接收的 `order.goodsAmount` 已是 `PromotionService`（见下）处理过促销折扣后的金额（见 `4.1` 节步骤4/5的调用顺序）；
- `PromotionService.matchActive(scope, scopeId)`：查询 `status=1` 且当前时间在 `[start_time, end_time]` 区间内、`scope`/`scope_id` 匹配的促销记录，供 §2.2 商品详情接口的 `activePromotion` 字段与 `OrderService` 下单结算（`4.1` 节步骤4）共用同一方法，避免两处各写一套匹配逻辑；命中多条同类型促销时取 `calculateDiscount` 结果最大的一条（对应 `10-数据库规范.md` §2.4.2 叠加规则）；`type=1`限时折扣/`type=4`组合套餐直接调整 `order_item.price`，`type=2`满减产出独立的 `promotionDiscountAmount`，`type=3`满赠仅返回"是否达到赠送门槛"供 `OrderService` 决定是否插入赠品 `order_item`（`is_gift=1`），本方法自身不写库；
- `PointsService.calculateDeduct(userId, goodsAmount)`：读取 `user.points`，按 `10-数据库规范.md` §2.4.3 "订单抵扣"规则计算 `min(points/100, goodsAmount*0.5)` 元的抵扣额度，向下取整到分；`PointsService.settleEarn(orderId, userId, payAmount)`（支付成功回调中调用，见 §4.4）按实付金额 1:1 写入正记录并累加 `user.points`；`PointsService.settleDeduct(userId, pointsUsed, orderId)`（下单成功时调用）写入负记录并扣减 `user.points`；`PointsService.clawback(orderId)`（退款流程中调用）按原订单关联的正记录金额写入负记录冲抵，`user.points` 最多扣至 `0`（不出现负数，取 `Math.max(0, points - clawbackAmount)`）；
- `FreightService.calculate`：解析 `freight_template.region_rule_json`（如 `[{"region":"华东","fee":8},{"region":"华南","fee":10}]`），先按 `10-数据库规范.md` §2.2.1 的省份-大区映射常量表将收货地址 `province` 转换为大区名，再匹配 `region_rule_json` 中对应大区的规则；未命中任何区域规则时使用 `default_fee`；`goodsAmount >= free_shipping_threshold` 时运费恒为 0；
- `LogisticsQueryService` 封装第三方物流查询 API 调用，失败时按 `05-详细设计说明书.md` §7 降级返回"物流信息暂不可用"而非抛出异常中断请求，建议对第三方调用加超时时间与有限次数重试（如最多重试2次，超时时间不超过3秒），避免拖慢整体接口响应。

## 10. 事务与并发控制总规范

| 场景 | 规范 |
|---|---|
| `@Transactional` 使用层级 | 统一加在 Service 层的业务方法上，不加在 Controller 或 Mapper 层 |
| 只读操作 | 查询类方法可标注 `@Transactional(readOnly = true)`，非必须但有助于数据库层优化 |
| 事务边界 | 事务范围内只包含数据库写操作；Redis 操作、第三方接口调用（物流查询等）放在事务外，避免长事务占用数据库连接 |
| 分布式锁 | 库存预扣减等强一致性场景用 Redisson 分布式锁；非强一致场景（如统计类计数）可用数据库 `UPDATE ... SET count = count + 1` 的原子更新代替加锁 |
| 乐观锁 | 本项目预扣减采用 Redis 原子操作而非数据库乐观锁（`version` 字段），因为库存的高频读写更适合 Redis；数据库真实库存扣减通过 `WHERE stock >= ?` 条件更新已足够防止超卖，无需额外引入 `version` 字段 |

## 11. 日志规范

- 使用 Logback（Spring Boot 默认），日志级别：`ERROR`（未预期异常、第三方调用失败）、`WARN`（业务异常如库存不足、优惠券不可用等预期内的失败）、`INFO`（关键业务节点：下单成功、支付回调、审核操作）、`DEBUG`（开发调试，生产环境关闭）；
- 涉及金额、库存扣减、支付回调的日志需包含订单号/流水号等关键标识，便于问题排查时按业务单号检索。

## 12. 单元测试规范

- 测试目录 `src/test/java`，与主代码包结构一一对应；
