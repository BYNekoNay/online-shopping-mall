### 0.2 通用问题分级（全程统一使用）

| 级别 | 定义 | 处置要求 |
|---|---|---|
| **P0（致命）** | 数据错误/丢失、资金相关、越权、崩溃、主链路不可用 | 立即修复，阻断发布 |
| **P1（严重）** | 核心功能异常、边界未覆盖、并发隐患、明显契约不一致 | 本阶段内修复 |
| **P2（一般）** | 代码规范、性能优化点、体验细节、测试缺失 | 汇总后统一处理 |

### 0.3 通用检查手段（每级都会用到）

1. **静态读码**：IDE + grep 定位（见各层检查点）
2. **动态验证**：启动后端（dev profile）→ 跑既有测试 → curl 实测接口
3. **契约比对**：后端字段 vs `docs/09`、`docs/16`；前端 api 消费字段 vs 后端返回
4. **数据核对**：SQL 脚本 vs 实体字段；Redis 键读写两侧一致
5. **问题留痕**：每条问题按模板登记（见 §0.4），结束后归档为报告

# 第一级：单模块层级（微观）

> 目标：确保每个模块内部"逻辑正确、分支完备、规则准确、状态可控"。
> 检查对象按业务重要性排序，先核心交易链路模块，后支撑模块。

## 1.1 后端模块检查清单（11 个）

### 1.1.0 通用检查项（每个模块都执行）

| # | 检查项 | 检查方法 | 判断标准 |
|---|---|---|---|
| G1 | 入参校验 | 检查 Controller/DTO 是否 @Valid + 字段注解（@NotNull/@NotBlank/@Min...） | 所有写接口有校验，非法入参返回 10001 而非 500 |
| G2 | 空值/越界处理 | 读 service 全部分支：查库返回 null、列表为空、数量≤0、金额为负 | 无 NPE 风险；业务非法输入有明确错误码 |
| G3 | 异常处理 | 业务失败是否抛 BusinessException + 对应 ErrorCode；未捕获异常是否被 GlobalExceptionHandler 兜底 | 无裸 try-catch 吞异常；错误码与 docs/09 §4 一致 |
| G4 | 事务边界 | @Transactional 位置正确（public、跨 mapper 写操作）；无自调用导致事务失效 | 写操作（增删改）均有事务；无自调用 |
| G5 | 权限标注 | 商家/管理员接口有 @RequireRole；消费者接口无多余角色限制 | 角色与 docs/09 接口权限声明一致 |
| G6 | 日志 | 关键操作（下单/支付/退款/审核）有日志；无敏感信息（密码/token）落日志 | 关键节点可追踪，日志无明文敏感字段 |
| G7 | 实体映射 | entity/VO/DTO 字段与数据库、接口规范一致 | 字段名/类型一致，无冗余或缺失 |

### 1.1.1 `user`（用户）— 优先级：高

| 检查点 | 具体核对 |
|---|---|
| 注册 | 用户名唯一校验（20003）、密码 BCrypt 加密、默认角色=1、禁用状态正确初始化 |
| 登录 | 密码校验、`LoginAttemptService` 防爆破（Redis `mall:login:fail` 计数/锁定）、JWT 签发内容（subject=userId、role 声明） |
| 账号状态 | 禁用/注销后旧 token 立即失效（`AccountStatusService.isActive` 在受保护路径校验） |
| 地址 CRUD | 默认地址唯一性（设置默认时其他地址取消默认）、删除默认地址的处理、越权访问他人地址（shopId/userId 校验） |
| 个人资料 | UpdateProfileDTO 字段校验、头像上传路径与访问 URL |

### 1.1.2 `product`（商品）— 优先级：高

| 检查点 | 具体核对 |
|---|---|
| 商品列表/搜索 | 分页参数边界、分类/价格区间/排序条件拼接、下架商品对消费者不可见（状态过滤） |
| 商品详情 | 多图轮播数据、SKU 列表与商品关联、库存展示口径（DB vs Redis） |
| 上下架 | 商家只能操作自家商品（shopId 校验）、状态流转合法、上架前审核状态 |
| 库存 | product.stock 与 sku.stock 关系、无 SKU 商品走 `StockService.deductProduct`（product 维度 key） |
| 评价 | 只能评价已收货订单的商品、幂等（同订单同商品不可重复评）、评分统计口径 |
| 分类 | 父子分类级联删除/禁用处理、分类下商品存在性检查 |

### 1.1.3 `order`（订单）— 优先级：最高（核心交易）

| 检查点 | 具体核对 |
|---|---|
| 下单前置校验 | 商品上下架（40002）、库存（40001）、SKU 与商品匹配（30004）、数量/金额计算 |
| 跨店拆单 | `createOrder` 按 shopId 分组 → `OrderGroupProcessor.processGroup` 每店独立事务；失败组回滚 + Redis 库存归还；积分/优惠券仅第一组应用（参数 applyPoints/applyCoupon 传递正确性） |
| 库存预扣 | `StockService.deduct` 锁获取失败（SYSTEM_BUSY）、Lua 返回 -1（不足）、低库存预警阈值；DB 二次校验 `UPDATE...WHERE stock>=?` |
| 支付 | `pay(orderId, payType)` 状态机（待付款→已付款）、重复支付拦截（50002）、支付后事务回调（afterCommit 做什么）、余额/模拟支付金额核对 |
| 状态机 | 待付款→待发货→已发货→已收货→已完成；取消/退款分支；每个状态转换的合法性与非法转换拦截（40004） |
| 超时取消 | `OrderTimeoutTask` 每分钟扫描：只取消"待付款"且超时 30 分钟；取消后归还库存/释放券 |
| 订单号 | `OrderNoGenerator` 唯一性（并发下不重复） |
| 收货/退款 | 确认收货只允许本人/已发货；退款金额上限校验、退款后库存恢复、退款状态流转（申请→审核→完成/拒绝） |

### 1.1.4 `recommend`（推荐）— 优先级：高（创新点）

| 检查点 | 具体核对 |
|---|---|
| 评分矩阵 | `buildRatingMatrix`：行为权重 1:3:5:4、时间衰减 `exp(-λ·Δt)`、归一化实现与 docs/12 一致 |
| 相似度 | UserCF 余弦相似度（K=20）、ItemCF（M=10）、倒排索引优化正确性 |
| 混合策略 | 动态 α（活跃 0.6/中等 0.4/不活跃走 ItemCF）分支条件与文档一致 |
| 冷启动 | `buildColdStartResults` 热门兜底 `销量×0.7 + 评分×0.3`；无行为用户不报错 |
| 缓存一致性 | `writeToRedis`/`readFromRedis` ZSet 结构、score 排序；`RecommendService.guessYouLike` 缓存未命中→实时计算→`RECOMMEND_GENERATING`(80001) 兜底 |

# 第二级：模块间联系层级（中观）

> 目标：验证模块间"契约一致、数据贯通、依赖正确、跨模块业务流连贯"。
> 本层最容易被忽略，也是 P0 类"看着都能跑、组合起来就坏"问题的重灾区。

## 2.1 检查对象

### 2.1.1 后端依赖矩阵

- 建立 11 个模块的注入依赖图（`grep "import com.pzhu.mall.modules.*"` 统计）；
- 重点：**order 模块**（注入 Coupon/Promotion/Points/Behavior/Freight/Logistics/Cart/Product 8 个外部服务，扇出最高）；
- 核对项：有无循环依赖（Spring 启动可验）、依赖是否单向、是否可降级（如 Behavior 埋点失败不应影响下单）。

### 2.1.2 接口契约一致性（前后端）

- 前端 `api/*.js`（12 个）逐一 vs 后端 Controller（接口路径、方法、入参结构、返回字段）；
- 重点字段核对：分页结构 `PageResult{records,total,current,size}`、统一响应 `Result{code,message,data}`、订单 VO 嵌套结构（OrderVO/OrderItemVO）；
- 对照 `docs/16-接口字段冻结核对记录.md` 的 96% 一致性基线，检查剩余 4% 差异点。

### 2.1.3 跨模块业务流走查（重点链路）

| 链路 | 涉及模块 | 重点核对 |
|---|---|---|
| ① 完整下单链路 | cart→product→order→marketing→logistics→behavior | 购物车数据如何传入（DTO 结构）、库存预扣与 DB 事务一致性、积分/券/促销只应用一次的保证、地址快照生成、购物车清理范围 |
| ② 支付→订单→库存 | order→product（库存） | 支付成功回调是否扣减 DB 库存（预扣转实扣）、失败重试幂等 |
| ③ 取消/超时→回退 | order→marketing（券）→product（库存） | 取消后：券是否回退、积分是否回退、库存是否归还、三者在同一事务还是补单 |
| ④ 退款链路 | order→product→marketing | 退款状态与订单状态联动（退款中/已退款）、库存恢复时机、金额上限 |
| ⑤ 行为→推荐 | behavior→recommend | 新行为写入后推荐缓存何时失效/重算（准实时策略）、`user_behavior` 增量触发 |
| ⑥ 统计→订单/行为 | statistics→order→behavior | 统计口径与订单/行为数据一致（如赠品剔除、退款剔除） |

### 2.1.4 共享状态与并发（Redis/分布式锁）

- 库存 key（`mall:stock:*`）读写两侧：StockService 扣减 vs 管理员改库存/退货恢复，是否有竞争；
- 优惠券核销 `user_coupon` 状态更新并发（是否加锁/乐观锁）；
- 推荐缓存 `mall:recommend:*` 写读一致（ZSet score 含义统一：score=相似度/热度，升序还是降序）；
- 分布式锁 key 命名空间隔离（sku 与 product 维度 key 不重叠，`stock:{}` vs `stock:product:{}`）。

### 2.1.5 数据传递与类型

- DTO→实体→VO 映射：金额 BigDecimal（不丢精度，禁止 double）、时间 LocalDateTime（时区）、ID 类型 Long 一致性；
- 跨模块 ID 传递（userId/shopId/orderId/productId）是否校验归属（防越权：商家接口查他人订单/商品）。

## 2.2 检查方法

1. 依赖注入图：grep 统计 + Spring 启动日志确认无循环依赖；
2. 契约比对：写脚本或手工逐接口对照 `docs/09`、`docs/16` 与前端 api 模块；
3. 链路走查：为 6 条重点链路各写一份"调用时序 + 数据流 + 状态变化"记录，标注每一步的文件:行号；
4. 并发验证：对下单/券核销接口做并发调用（如 20 并发），观察库存/券是否超发、有无死锁；
5. 跨模块测试：补充集成测试（如"下单→支付→发货→确认收货→评价"全链路用例）。

## 2.3 第二级判断标准（验收口径）

1. 依赖矩阵无循环依赖、无跨层调用（controller 不直接调 mapper）；
2. 前后端契约差异清单 = 0（或差异均为已登记的文档偏差）；
3. 6 条链路走查记录齐全，链路中每步状态转换合法；
4. 并发测试无超卖/超发/死锁；
5. 越权校验在每个跨模块入口存在（订单/商品/店铺归属）。

## 2.4 第二级预期产出

- 模块依赖矩阵图 + 循环依赖核查记录；
- 前后端接口契约差异清单（并回写 docs/16 差异登记）；
- 6 份链路走查记录（时序+数据流+状态）；
- 并发测试结果（指标：扣减正确率、锁等待时间、错误码分布）；
- 《第二级问题汇总》P0/P1/P2 分级。

# 第三级：整体系统层级（宏观）

> 目标：端到端视角确认"需求覆盖、边界兜底、性能并发、架构支撑"，并输出最终汇总与修复优先级。

## 3.1 检查对象

### 3.1.1 需求覆盖度（对照 docs/03 与 docs/19）

- 建立 **需求→接口→页面** 覆盖矩阵：FR-C-*（消费者）/ FR-M-*（商家）/ FR-A-*（管理员）逐条核对实现位置与状态；
- 重点核对创新点：①UserCF+ItemCF 混合 ②行为权重差异化 ③冷启动 ④准实时缓存（docs/19 §3.4 已列实现位置，复核一遍真实代码）；
- 检查"任务书 7.1~7.6"扩展场景（优惠券/促销/积分/物流/安全/统计）是否全部落地。

### 3.1.2 全局异常与边界

- `GlobalExceptionHandler` 覆盖面：BusinessException / 参数校验异常（MethodArgumentNotValidException）/ 未捕获 Exception / 404；
- 边界场景清单：未登录访问受保护接口、禁用账号访问、库存为 0、优惠券过期、订单超时竞态（取消瞬间支付）、并发下单同一 SKU、上传超限（10MB/20MB）、非法参数注入（SQL 注入/XSS 样本）；
- 逐条用 curl 或前端复现，确认返回错误码正确且前端有对应提示。

### 3.1.3 性能与并发

| 检查点 | 方法 | 标准 |
|---|---|---|
| 推荐接口 RT | 缓存命中/未命中两种情况实测 | 命中 <50ms，未命中可接受但有兜底提示 |
| 商品列表/搜索 | 分页 SQL 执行计划（索引） | 无全表扫描热点；`product/category/sku` 索引覆盖查询条件 |
| 下单并发 | 压测（如 50 并发×同一 SKU） | 无超卖；无死锁；错误码分布合理（成功/库存不足/系统繁忙） |
| 缓存命中率 | Redis `mall:recommend:*` 过期与刷新节奏 | 热门商品缓存稳定命中 |
| 定时任务 | 3 个任务执行时长与重叠 | 任务不重叠、不阻塞主业务 |
| 前端性能 | dist 体积、首屏加载 | ECharts 等大库考虑按需引入（改进点登记） |

### 3.1.4 架构支撑性复核

- 分层是否被破坏（controller 直连 mapper、service 直连 service 跨层）；
- 横切能力完备性（认证/鉴权/日志/异常/安全头）；
- 配置管理：dev/prod profile 隔离、密钥无硬编码（grep 敏感关键字：password/secret/token 的字符串字面量）；
- 部署链路：docker-compose 服务依赖（healthcheck）、nginx 路由与安全头、上传目录持久化（volume 缺失会丢图片）。

### 3.1.5 安全复核（对照 docs/18 基线 B+）

- 越权（水平/垂直）：抽查 3 类接口（商家看他人订单、用户改他人地址、管理员接口匿名访问）；
- 注入：SQL 拼接点扫描（`${}` 在 XML 中的使用）、XSS 样本注入；
- 敏感信息：日志/错误响应中 token、密码、支付信息泄露；
- 认证绕过：白名单路径绕过尝试（如 `/api/products/../admin/xxx`、大小写变体）。

## 3.2 检查方法

1. **端到端冒烟**：按 07-用户操作手册 走完 3 个角色核心流程（消费者：注册→浏览→加购→下单→支付→收货→评价→推荐；商家：入驻→发布→发货→统计；管理员：审核→看板→日志），每个流程记录通过/失败；
2. **需求覆盖矩阵**：表格逐条打勾（实现/未实现/偏差）；
3. **边界注入测试**：用 curl 脚本批量执行边界样本；
4. **并发/压测**：下单场景并发脚本，记录结果；
5. **静态扫描**：grep 敏感模式 + 依赖安全检查（可选 OWASP Dependency-Check）；
6. **代码走查评审会**：针对第一、二级汇总的疑难问题，二次确认定性。

## 3.3 第三级判断标准（验收口径）

1. 需求覆盖矩阵：任务书 + docs/03 全部需求条目有实现落点，偏差均有说明；
2. 边界样本全部返回正确错误码，前端均有对应友好提示；
3. 并发压测无 P0 级问题（无超卖、无数据错乱）；
4. 无硬编码密钥、无 SQL 注入点、无越权漏洞（或已全部修复）；
5. 分层未被破坏，架构支撑业务目标。

## 3.4 第三级预期产出

- 《需求覆盖矩阵》（需求→接口→页面，三态：✅实现/⚠️偏差/❌缺失）；
- 《边界与异常测试记录》（样本、期望、实际、结果）；
- 《性能与并发测试报告》（RT、QPS、错误码分布、缓存命中率）；
- 《安全复核记录》；
- **《系统检查汇总报告》**：全部问题按 P0/P1/P2 汇总，给出修复优先级与排期建议。

# 4. 汇总输出与修复优先级

## 4.1 汇总报告结构

```
1. 检查范围与结论概览（三级完成情况、问题总数、P0/P1/P2 分布）

4. 复验计划（修复后按受影响链路回归）
5. 遗留风险与后续改进项（架构层面，如 outbox、增量推荐计算）
```

## 4.2 修复优先级规则

| 优先级 | 触发条件 | 处理时限 |
|---|---|---|
| P0 | 数据错误/资金/越权/主链路不可用/并发超卖 | 立即修复 + 当日复验 |
| P1 | 核心功能分支缺失/契约不一致/边界未覆盖 | 阶段内修复 |
| P2 | 规范/性能优化/体验/测试补充 | 汇总后统一处理 |

## 4.3 复验策略

- 每个修复点：单测/集成测试补用例 → 跑既有测试（37 后端 + 2 前端 + 10 集成基线）→ 受影响链路回归；
