# 系统架构梳理报告

> **日期**：2026-08-12
> **范围**：基于源码（backend 164 个 Java 类 / frontend 44 个 .vue）+ 部署配置 + 数据库脚本的系统性架构分析

---

## 1. 总体架构：分层 + 模块化单体

系统采用 **B/S 架构、前后端分离、模块化单体（Modular Monolith）**：

```
┌─────────────────────────────────────────────┐
│ 前端  Vue3 + Element Plus + Pinia + ECharts  │  消费者端 / 商家端 / 管理员端
├─────────────────────────────────────────────┤
│ 接入层  Nginx（静态资源 + /api 反向代理）     │
├─────────────────────────────────────────────┤
│ 后端  Spring Boot 2.7（模块化单体）          │  11 个业务模块 + 横切基础设施
├─────────────────────────────────────────────┤
│ 数据层  MySQL 8.0（25 表）+ Redis 7          │
└─────────────────────────────────────────────┘
```

架构形态选择说明：**没有微服务拆分**，而是模块化单体——推荐算法、营销、订单等以 Java 包划分模块，通过 Spring Bean 注入协作。对毕业设计规模是合理的：无服务间通信开销、事务可控、单机 Docker 即可部署；代价是模块间依赖需要靠包边界纪律约束。

## 2. 后端架构

### 2.1 模块划分（11 个业务模块 + 横切层）

| 模块 | 职责 | 关键类 |
|---|---|---|
| `user` | 注册/登录/资料/收货地址 | UserService、LoginAttemptService（防暴力破解）、AddressService |
| `shop` | 商家入驻、店铺信息/装修 | ShopService（入驻审核闭环） |
| `product` | 商品/SKU/分类/评价/搜索 | ProductService、ReviewService、CategoryService |
| `cart` | 购物车 | CartService（含库存校验） |
| `order` | 下单/支付/发货/收货/退款 | OrderService(706行)、OrderGroupProcessor(跨店拆单)、StockService(Redis预扣)、OrderTimeoutTask(超时取消) |
| `recommend` | 推荐算法引擎 | RecommendCalculateService(819行)、RecommendService、RecommendRefreshTask |
| `marketing` | 优惠券/促销/积分 | CouponService、PromotionService、PointsService |
| `logistics` | 运费模板/物流查询 | FreightService、LogisticsQueryService |
| `behavior` | 用户行为埋点 | BehaviorService（浏览/收藏/购买/评价 + 页面访问） |
| `statistics` | 商家销售统计/平台看板 | MerchantStatisticsService、PlatformStatisticsService、StatisticsSnapshotTask |
| `admin` | 用户/商品/店铺审核、系统配置、操作日志、字典 | Admin*Controller、OperationLogService |

### 2.2 分层规范（每个模块内部）

```
controller（入参 DTO + 出参 VO）
    ↓
service（业务逻辑，@Transactional 事务边界）
    ↓
mapper（MyBatis-Plus，XML 复杂查询在 resources/mapper/**）
    ↓
entity（数据库实体）
```

横切基础设施（`common/` + `config/` + `security/`）：
- **统一响应**：`Result<T>`（code/message/data）+ `PageResult<T>` 分页
- **错误码**：`ErrorCode` 枚举，业务码分段（10xxx 通用 / 20xxx 用户 / 30xxx 商品 / 40xxx 订单 / 60xxx 营销 / 80xxx 算法）
- **异常体系**：`BusinessException` + `GlobalExceptionHandler` 全局兜底
- **安全**：`JwtInterceptor`（认证）+ `RequireRole` 注解 + `RoleCheckAspect`（角色鉴权）+ `LoginUserContext`（ThreadLocal）
- **审计**：`OperationLogService` 操作日志；`SecurityHeadersFilter` 安全响应头

### 2.3 认证授权模型（双保险）

```
请求 → JwtInterceptor（HandlerInterceptor）
        ├─ 白名单（/api/auth/login、/api/products、/api/recommend/guess-you-like…）
        │    └─ 可选登录：有有效 token 则写入上下文，否则按匿名处理
        ├─ 非白名单：必须携带有效 Bearer Token，且账号未被禁用
        │    └─ 解析 userId + role 写入 LoginUserContext
        └─ afterCompletion 清理 ThreadLocal（防泄漏）

Controller 方法 → @RequireRole({2}) → RoleCheckAspect（@Before AOP）
        └─ 比对当前用户角色与允许角色，不匹配抛 10003 FORBIDDEN
```

- 角色约定：**1=消费者，2=商家，3=管理员**
- JWT 有效期 7 天（604800s），密钥通过 `JWT_SECRET` 环境变量注入（dev 有独立默认值，prod 必须显式注入）
- 登录失败计数走 Redis（`mall:login:fail`），防暴力破解

### 2.4 定时任务（3 个）

| 任务 | 调度 | 职责 |
|---|---|---|
| RecommendRefreshTask | 每天 02:00 | 全量重算推荐结果 + 缓存热门商品 |
| OrderTimeoutTask | 每分钟 | 超时未支付订单自动取消 + 归还库存 |
| StatisticsSnapshotTask | 每天 01:00 / 01:30 | 商家销售/平台统计快照 |

## 3. 前端架构

### 3.1 工程组织（Vite + Vue3 组合式 API）

```
src/
├── api/         12 个 API 模块（按业务域：product/order/cart/recommend…）
├── router/      index.js 三端路由 + 全局守卫
├── store/       Pinia：user（登录态）/ cart / app / merchant
├── views/       consumer(7域) / merchant(5域) / admin(6域) / common(登录注册403)
├── layouts/     3 个端布局（ConsumerLayout / MerchantLayout / AdminLayout）
├── components/  RecommendList.vue（推荐位组件）
├── utils/       request.js（axios 封装）
├── plugins/     page-view.js（页面浏览埋点）
├── mock/        11 个 Mock 模块（vite-plugin-mock，前后端并行开发用）
└── constants/   product.js（状态字典）
```

### 3.2 请求封装（`utils/request.js`）

- baseURL `/api`，10s 超时
- 请求拦截：localStorage 读 token → 注入 `Authorization: Bearer`
- 响应拦截（统一错误处理）：
  - `code===0` 放行；业务错误 toast
  - `10003` → 跳 /403；`10002`/401 → 登出 + 跳 /login
  - 网络错误 → 友好提示

### 3.3 路由权限（前端守卫）

- `meta.requiresAuth`：未登录跳登录页（带 redirect 回跳）
- `meta.roles`：角色不匹配跳 /403（子路由可覆盖父路由声明，如商家入驻页允许消费者访问）
- 三端入口：`/`（消费者）、`/merchant`（商家，role=2）、`/admin`（管理员，role=3）

## 4. 数据架构

### 4.1 MySQL：25 张表

**用户域**：`user`、`address`
**商品域**：`category`、`product`、`sku`、`review`、`search_history`
**交易域**：`cart`、`orders`、`order_item`、`payment`、`refund`
**店铺/物流域**：`shop`、`freight_template`、`logistics`
**营销域**：`coupon`、`user_coupon`、`promotion`、`points_record`
**算法/行为域**：`user_behavior`、`user_score`、`recommend_result`、`page_view_log`
**系统域**：`system_config`、`dict`、`operation_log`

特点：
- 逻辑删除（MyBatis-Plus `logic-delete-field: isDeleted`）
- 复杂 JSON 字段用 `JsonTypeHandler` 处理（如促销规则、店铺装修配置）
- 订单表含快照字段（address_snapshot 等），保证历史订单不受地址/价格变更影响

### 4.2 Redis 键设计

| 键前缀 | 用途 |
|---|---|
| `mall:recommend:{userId}` | 用户"猜你喜欢" ZSet 缓存 |
| `mall:recommend:similar:{productId}` | 相似商品 ZSet 缓存 |
| `mall:recommend:hot:products` | 热门商品缓存 |
| `mall:stock:{skuId}` / `mall:stock:product:{productId}` | **库存预扣减**（key 不设 TTL，防超卖） |
| `mall:lock:stock:{...}` | Redisson 分布式锁 |
| `mall:statistics` | 统计快照缓存 |
| `mall:search:history:{userId}` | 搜索历史 |
| `mall:login:fail:{username}` | 登录失败计数 |

### 4.3 库存一致性方案（防超卖）

```
下单 → Redisson 分布式锁（tryLock 3s 等待/10s 租约，看门狗续期）
     → Lua 脚本原子执行【懒加载 DB 库存 → 校验 → 扣减】
     → 失败返回 false（库存不足）；成功进入 DB 事务
     → DB 层 UPDATE ... WHERE stock >= ? 二次校验（最终一致性兜底）
支付超时/取消 → 归还（INCR）
```

## 5. 关键业务链路

### 5.1 下单链路（跨店铺拆单）

```
CreateOrderDTO → OrderService.createOrder()
  ├─ 商品合法性/上下架校验
  ├─ 按 shopId 分组（Map<shopId, List<ProductItemDTO>>）
  ├─ StockService 预扣库存（每个 SKU 加锁）
  └─ OrderGroupProcessor.processGroup() × N（每个店铺一个独立事务）
        └─ 创建 Order + OrderItem（含赠品行 is_gift）→ 促销结算（限时折扣/满减/满赠）
           → 积分抵扣 → 优惠券核销 → 清理购物车
     任一店铺组失败 → 该组回滚，其余组正常；Redis 库存统一归还
幂等：24h 幂等 key；超时：OrderTimeoutTask 每分钟扫描取消
```

### 5.2 推荐链路（UserCF + ItemCF 混合）

```
数据采集：BehaviorService（浏览/收藏/购买/评价，权重 1:3:5:4，时间衰减）
    ↓
评分矩阵 buildRatingMatrix() → 归一化
    ↓
相似度计算：UserCF（余弦相似度，K=20 近邻）
            ItemCF（商品相似度，M=10）
    ↓
混合策略：按用户活跃度动态 α（活跃 α=0.6，中等 0.4，不活跃走 ItemCF）
    ↓
冷启动：新用户/行为稀疏 → 热门商品兜底（热度 = 销量×0.7 + 评分×0.3）
    ↓
结果写库 recommend_result + 写 Redis ZSet（准实时）
    ↓
对外：guessYouLike() 先读 Redis 缓存，未命中触发实时计算（RECOMMEND_GENERATING 兜底）
```

### 5.3 统计链路

- 商家统计：`MerchantStatisticsService`（销售总额/订单量/热销 TOP10/日周月趋势）
- 平台看板：`PlatformStatisticsService`（GMV/用户增长/转化率/推荐效果）
- 每日 01:00 快照落库 + Redis 缓存（`STATISTICS_NOT_READY` 兜底）

## 7. 安全设计（评级 B+，见 docs/18）

- 认证：JWT + 账号状态实时校验（禁用立即失效）
- 鉴权：AOP 角色切面 + 白名单可选登录 + 防大小写绕过（M1 修复）
- 存储：BCrypt 密码哈希；JWT 密钥环境变量注入（无硬编码）
- Web：XSS/SQL 注入（MyBatis-Plus 参数化）、安全响应头（nosniff/X-Frame-Options 等）、CSRF（同源部署）
- 业务：登录防爆破、库存防超卖、操作日志审计、敏感信息不落日志

## 8. 架构评价

### 优势
1. **模块划分清晰**：11 个业务模块边界合理，controller/service/mapper 分层统一
2. **文档-代码一致性好**：接口字段冻结（docs/16）、算法评估（docs/17）、安全自查（docs/18）均已回检
3. **关键难点有工程化方案**：防超卖（Redisson+Lua+DB 二次校验）、跨店拆单（独立事务组）、推荐冷启动/准实时
4. **安全细节到位**：硬编码密钥清除、环境变量注入、ThreadLocal 清理、日志脱敏

### 可改进点（非阻塞）
1. **模块间耦合**：OrderService 直接注入 Coupon/Promotion/Points/Behavior 等 8 个外部服务，营销结算逻辑可抽成独立结算组件，降低订单模块的扇出
2. **本地事务 + Redis 的一致性问题**：Lua 扣库存成功但 DB 事务失败时依赖"手动归还"，可引入消息/事务性发件箱（outbox）模式彻底解耦
3. **推荐性能**：`calculateForAll()` 全量重算（每天 2 点），数据量大时可改为增量计算 + 分批
4. **前端包体积**：ECharts 全量引入，可改按需引入（vite-plugin 拆包）提升首屏性能
5. **测试覆盖**：37 个后端单测集中在核心服务，controller 层与前端组件层覆盖偏薄
