# 代码与业务流程检查方案（体系化·可执行版）

> 版本：v1.0 ｜ 制定日期：2026-08-14 ｜ 状态：生效
> 关联文档：docs/22（三级递进检查计划）、docs/25（代码审查方案）、docs/24（修复执行报告）、docs/28（动态验证报告）、docs/29（复检报告）
> 适用对象：本项目全部后端（Spring Boot 2.7.18 / 11 模块）、前端（Vue 3 / 三端）、数据层（MySQL 25+1 表 / Redis）、部署（Docker Compose）
> 本方案是 docs/22 的**常态化落地版**：把一次性三级检查固化为可重复执行、可自动化的检查体系。

## 0. 方案总览

### 0.1 检查体系架构

```
┌─────────────────────────────────────────────────────────────────┐
│                   检查体系（五层，从下到上）                        │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 5. 持续改进闭环：问题登记→分级→分配→跟踪→复检→反馈设计      │  │
│  └───────────────────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 4. 质量指标：覆盖率/零严重缺陷/通过率/成功率 量化门槛        │  │
│  └───────────────────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 3. 工具与自动化：静态扫描+单测+CI 门禁+定时触发+报告        │  │
│  └───────────────────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 2. 业务流程检查：核心链路/节点校验/异常/一致性/状态机/边界   │  │
│  └───────────────────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 1. 代码检查：规范审查→静态分析→单测→集成测试→Code Review    │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 0.2 执行节奏（三类触发）

| 触发类型 | 时机 | 范围 | 工具 |
|---|---|---|---|
| **提交级**（每次 push/PR） | 开发者本地 + CI | 变更文件 | lint、checkstyle、spotbugs、单测 |
| **迭代级**（每个迭代末，如每 2 周） | 迭代评审会前 | 本迭代全部改动 | 全部工具 + 代码评审 |
| **发布级**（版本发布前） | Release 分支打 tag 前 | 全量 | 全量检查 + 业务流程演练 + 动态验证 |

### 0.3 问题分级（全程统一，与 docs/22 §0.2 一致）

| 级别 | 定义 | 处置时限 | 阻断门禁 |
|---|---|---|---|
| **P0** | 数据丢失/资金错误/安全漏洞/系统不可用 | 立即修复 | 阻断合并、阻断发布 |
| **P1** | 主流程功能错误、明确的需求未实现、严重一致性缺陷 | 3 个工作日 | 阻断发布 |
| **P2** | 体验/健壮性/代码质量类，不影响主流程 | 2 个迭代内 | 不阻断，纳入排期 |

## 1. 代码检查（Code Inspection）

### 1.1 五阶段流水线（执行顺序固定）

```
规范审查 → 静态分析 → 单元测试 → 集成测试 → Code Review
  (1)      (2)      (3)      (4)       (5)
```

### 1.2 阶段 1：代码规范审查（Style & Convention）

**检查对象**：全部后端 Java、前端 JS/Vue 源码。

**检查清单（C 系列）**：

| 编号 | 检查项 | 后端标准 | 前端标准 |
|---|---|---|---|
| C-01 | 命名规范 | 类 PascalCase、方法/变量 camelCase、常量 UPPER_SNAKE；包名 `com.pzhu.mall.modules.*` | 组件 PascalCase、函数/变量 camelCase；`api/*.js`、`views/*`、`components/*` 目录语义 |
| C-02 | 格式规范 | 缩进 4 空格、行宽 120、空行分组、`{}` 风格 | Prettier 默认（缩进 2 空格、单引号、行宽 80/100） |
| C-03 | 注释规范 | 类/公共方法必须有 Javadoc；业务规则、魔法数字、复杂分支必须注释 | 复杂函数 JSDoc；组件 props/事件说明 |
| C-04 | 导入规范 | 无 `*` 通配导入；未使用导入必须移除；按项目/三方/JDK 分组 | 同后端（eslint 检测） |
| C-05 | 魔法值 | 状态码/错误码/业务常量必须用枚举或常量类（`ErrorCode`、`OrderStatus`、`RedisKeyPrefix`） | 状态文案映射用常量表（`STATUS_MAP`） |
| C-06 | 废弃代码 | 禁止保留注释掉的代码块、未使用的 import/方法/字段 | 同后端 |
| C-07 | TODO/FIXME | 必须关联问题编号（`// TODO #O-03`）并登记 | 同后端 |
| C-08 | 前端模板规范 | — | `<script setup>` 优先；样式 scoped；无内联样式硬编码色值 |

**执行方式**：后端 `mvn checkstyle:check`（error 级，`checkstyle.xml` 硬规范）；前端 `npm run lint`（eslint）+ `npm run format`（prettier，可先 `--check` 后 `--write`）。

**通过条件**：checkstyle 0 error；eslint 0 error（warning 允许但需说明）；prettier `--check` 无差异（或已格式化）。

**责任人**：开发者自查（提交前）→ CI 强制（合并前）。

### 1.3 阶段 2：静态分析检查（Static Analysis）

**检查对象**：后端全部 Java；前端（eslint 已覆盖规范，可加 `vue-tsc` 类型检查）。

**工具与规则**：

| 工具 | 覆盖缺陷类型 | 本项目配置 | 通过条件 |
|---|---|---|---|
| **SpotBugs** | 空指针、资源泄漏、集合浅拷贝、错误 equals/hashCode、并发问题、SQL 注入风险 | `spotbugs-maven-plugin` 4.9.8.5，`effort=Max`、`threshold=Low`、`spotbugs-exclude.xml` 存量豁免 | **新增 0 严重缺陷（High/Medium）**；存量豁免项需每迭代复核清单 |
| **ESLint**（前端） | 未定义变量、重复声明、不安全的 `v-html`、隐式 any | `eslint.config.js` | 0 error |
| 人工复核 | 业务逻辑类缺陷（工具测不出的） | 见 1.6 Code Review | — |

**关键风险点**：空指针（尤其 DTO→实体转换、Redis 反序列化）、资源未关闭（`try-with-resources`）、`BigDecimal` 精度、并发容器误用。

**通过条件**：SpotBugs 新增缺陷 0 条 High/Medium；前端 eslint 0 error。

**责任人**：CI 自动执行；开发者对新增告警负责清零。

### 1.4 阶段 3：单元测试（Unit Test）

**测试对象**：Service 层核心逻辑、Mapper SQL 行为、工具类、前端 API 封装/路由守卫。

**测试基础设施**（已就绪）：

| 项 | 配置 |
|---|---|
| 后端 | JUnit 5 + Mockito；`./mvnw test`（**当前 207 用例全绿**） |
| 前端 | Vitest + @vue/test-utils；`npm test`（当前 14 用例全绿） |
| 覆盖率 | JaCoCo（backend，`jacoco-maven-plugin`）；vitest `coverage` 可选 |

**单测清单（T 系列）**：

| 编号 | 检查项 | 判断标准 |
|---|---|---|
| T-01 | 每个 Service 公共方法至少 1 个正向用例 | 方法覆盖 ≥ 覆盖率的基线要求 |
| T-02 | 每个分支/异常至少 1 个用例 | `BusinessException`、边界值、非法入参 |
| T-03 | 资金类逻辑必须有边界用例 | 金额 0/负数/超大、精度比较用 `compareTo` |
| T-04 | 状态机必须有合法/非法流转用例 | 见 §2.4 状态机清单 |
| T-05 | 前端关键页面逻辑（订单提交、券计算）有组件测试 | 新增页面随迭代补齐 |
| T-06 | Mock 必须验证关键交互 | `verify` 关键调用（如库存扣减、幂等键写入） |

**通过条件**：`mvn test` 100% 通过、0 失败 0 错误；新增代码行覆盖率 ≥ 80%（详见 §4）。

**责任人**：开发者写测试（与实现同 PR）；CI 执行；迭代评审复核覆盖率。

### 1.5 阶段 4：集成测试（Integration Test）

**测试对象**：Controller→Service→Mapper 全链路、跨模块调用、Redis/DB 真实交互。

**现有资产**：`MainChainIntegrationTest`（主链路冒烟）；docs/28 动态验证脚本（真实环境端到端）。

**集成测试清单（IT 系列）**：

| 编号 | 链路 | 验证点 |
|---|---|---|
| IT-01 | 注册→登录→加购→下单→支付→收货→评价→推荐 | 全链路状态正确、推荐结果刷新 |
| IT-02 | 下单（跨店铺拆单） | 分组正确、每店独立事务、失败组回滚 |
| IT-03 | 取消/超时取消 | 库存归还、券释放、积分返还、幂等 |
| IT-04 | 退款闭环 | 审核通过→库存恢复（DB+Redis）→积分扣回 |
| IT-05 | 优惠券链路 | 领取→限领→估价→下单核销→取消释放 |
| IT-06 | 满赠促销 | 达标赠品行生成、库存预扣/回滚、评价拦截 |
| IT-07 | 并发下单 | 50 并发同 SKU，Redis 预扣 + DB 实扣零超卖 |
| IT-08 | 推荐准实时 | 购买行为后 recommend_result 及时更新 |

**执行方式**：本地环境（MySQL/Redis）+ 自动化脚本（docs/28 §7 脚本化）；CI 可选跑轻量链路。

**通过条件**：全部链路断言通过；并发压测零超卖。

**责任人**：质量负责人（QA/项目负责人）执行；开发者配合造数。

### 1.6 阶段 5：代码评审（Code Review）

**评审流程**（3 个强制节点 + 1 个定期节点，与 docs/25 §2.1 对齐）：

```
开发者自检（提交前 checklist）→ CI 门禁（自动）→ PR 评审（合并前，≥1 人批准）→ 迭代评审会（每迭代）
```

**评审 Checklist（PR 强制，前后端共用）**：

| 维度 | 检查项 |
|---|---|
| 功能正确性 | 需求是否完整实现？分支/边界是否覆盖？ |
| 数据安全 | 越权（IDOR）防护？输入校验？敏感信息不落日志？ |
| 一致性 | 与 docs/16 接口契约一致？错误码语义正确？ |
| 事务/并发 | `@Transactional` 边界？Redis 操作是否在事务外？锁粒度？ |
| 性能 | N+1 查询？批量处理？索引使用？ |
| 可维护性 | 命名/注释/复杂度（圈复杂度 ≤ 10）？重复代码？ |
| 测试完备 | 是否带测试？覆盖关键分支？ |

**角色与责任**：

| 角色 | 职责 | 评审重点 |
|---|---|---|
| 开发者（Author） | 自检、自测、发起 PR | 完整自检 |
| 评审人（Reviewer，≥1） | 代码走查、提出修改意见、批准合并 | 正确性/安全/一致性 |
| 迭代负责人（迭代评审会） | 汇总质量报告、跟踪遗留问题 | 指标/趋势 |
| CI | 自动门禁（lint/checkstyle/spotbugs/单测/构建） | 硬性门槛 |

**通过条件**：CI 全绿 + 至少 1 名评审人批准 + 无未解决 P0/P1 评论。

## 2. 业务流程检查（Business Process Verification）

### 2.1 核心业务流程清单（B 系列）

以"一次完整交易"为纲，覆盖 6 条核心链路（编号与 docs/22 二级对齐）：

```
B-1 注册登录 → B-2 浏览→加购→下单 → B-3 支付 → B-4 取消/超时
B-5 退款 → B-6 收货→评价→行为→推荐
```

### 2.2 关键节点验证方法（每个节点四件套）

对每个业务节点，统一按 **输入校验 → 异常路径 → 数据一致性 → 状态机流转** 四项验证：

| 验证维度 | 方法 | 示例（下单节点） |
|---|---|---|
| **输入/输出校验** | 入参注解校验（@Valid/@NotBlank/@Size）+ 业务规则校验 + 返回值断言 | 数量>0、SKU 存在、商品在售、地址归属本人、`requestId` 幂等 |
| **异常处理路径** | 枚举异常场景，断言错误码与提示；吞异常点必须补日志 | 库存不足→40001；券已核销→对应错误码；`catch` 必须 `log.error(e)` |
| **数据一致性** | 事务边界、Redis 与 DB 双写一致性、幂等键、乐观锁 | 支付实扣库存（DB+Redis）；退款恢复双口径；防超卖 GREATEST |
| **状态机流转** | 合法/非法流转表（见 §2.4） | 0→1→2→4→7 合法；2→5 非法（已支付不可取消） |

### 2.3 各链路检查清单（B 系列明细）

| 编号 | 链路/节点 | 关键验证点 | 风险等级 |
|---|---|---|---|
| B-1a | 注册 | 用户名/手机号唯一（预查+索引双保险）、密码强度、验证码 | P1 |
| B-1b | 登录 | 防爆破（用户名+IP 限流）、XFF 伪造防护、BCrypt | P1 |
| B-1c | 登录态 | JWT 过期、角色变化后 token 失效策略 | P1 |
| B-2a | 浏览/搜索 | 列表过滤在售/审核通过、搜索历史去重、埋点 userId 服务端取值 | P2 |
| B-2b | 加购 | 原子 upsert、上限 99、越权防护、SKU 失效处理 | P1 |
| B-2c | 估价 | 优惠券语义（模板 ID vs 用户券 ID）、赠品提示、运费模板 | P1 |
| B-2d | 下单 | 防价格篡改（DB 单价）、跨店拆单、Redis 预扣+DB 实扣、幂等键 | **P0** |
| B-3a | 支付 | 幂等（防重复支付）、payment 落库、状态机 0→1、积分结算 | **P0** |
| B-3b | 库存实扣 | 原子 UPDATE（WHERE stock>=?）、product.stock 与 sku.stock 双口径 | **P0** |
| B-4a | 用户取消 | 状态机校验、券/积分/库存归还、afterCommit Redis | P1 |
| B-4b | 超时取消 | 定时任务扫描、与手动取消互斥（状态原子更新） | P1 |
| B-5a | 退款申请 | 幂等键后置（校验通过才写）、金额校验、越权 | P1 |
| B-5b | 退款审核 | 库存恢复（DB+Redis afterCommit）、积分扣回、状态 7 | P1 |
| B-6a | 收货 | 状态机 1→2→4（或 3 死状态核对）、仅支付后可收货 | P2 |
| B-6b | 评价 | 仅本人订单项、仅一次、赠品行拦截、评分 1~5 | P2 |
| B-6c | 行为→推荐 | 购买后准实时刷新、曝光/点击落库、行为权重 1:3:5:4 | P1 |
| B-7 | 统计看板 | 商家口径 status IN(1,2,3,4,6)、平台 GMV 口径一致、CTR 真实口径 | P1 |

### 2.4 状态机流转检查表（S 系列）

| 状态机 | 合法流转 | 非法流转（必须拦截） | 并发防护 |
|---|---|---|---|
| 订单（orders.status） | 0→1（支付）→2（发货）→4（收货）→7（退款完成）；0→5（取消） | 0→4、1→5、2→7（未退款直接终态）、7→* | `UPDATE ... WHERE status=?` 原子更新 |
| 退款（refund.status） | 0→1（通过）/2（驳回） | 已终态重复审核、金额变更 | 乐观锁/状态条件更新 |
| 店铺（shop.status） | 0→1（通过）/2（驳回）；驳回→0（重提） | 已通过再驳回、并发双审 | 原子审核 |
| 商品（product.status） | 0（待审）→1（在售）/3（驳回）；1→2（下架） | 下架/待审直链可购 | 状态条件更新 |
| 优惠券（user_coupon.status） | 0（未用）→1（已用）→2（释放）；0→2 | 已用再核销 | `WHERE status=0` 原子核销 |

**验证方法**：为每个状态机编写合法/非法流转用例（T-04 落地为单测），关键并发流转用集成测试（IT-07）验证。

### 2.5 边界条件覆盖清单（E 系列，对齐 docs/28 动态验证）

| 编号 | 边界场景 | 预期行为 |
|---|---|---|
| E-01 | 未登录访问受保护接口 | 401/10002 引导登录 |
| E-02 | 越权访问他人订单/地址/购物车 | 403/对应错误码 |
| E-03 | 非法参数（数量 0/负数、超长文本、非法枚举） | 400 参数校验错误，信息明确 |
| E-04 | 推荐 num 超限 | 钳制到上限 |
| E-05 | 库存临界（恰好 1 件并发 2 单） | 恰好 1 单成功 |
| E-06 | 优惠券临界（门槛边界、过期瞬间） | 精确比较，无边界误差 |
| E-07 | 金额精度（0.1+0.2 类浮点） | BigDecimal 无精度丢失 |
| E-08 | 时间边界（促销开始/结束瞬间） | 左闭右开语义正确 |
| E-09 | 幂等重放（同 requestId 二次提交） | 返回原结果，不重复扣库存 |
| E-10 | 满赠临界（恰达门槛/差 1 分） | 精确判定 |

## 3. 工具与自动化（Tools & Automation）

### 3.1 工具矩阵

| 类别 | 工具 | 覆盖阶段 | 触发方式 |
|---|---|---|---|
| 代码规范 | ESLint + Prettier（前端）、Checkstyle（后端） | 1 规范 | 本地钩子 + CI |
| 静态分析 | SpotBugs（后端）、ESLint 规则（前端） | 2 静态 | CI |
| 单元测试 | JUnit5+Mockito（后端）、Vitest（前端） | 3 单测 | 本地 + CI |
| 覆盖率 | JaCoCo（后端）、Vitest coverage（前端，可选） | 3 单测 | CI 生成报告 |
| 集成测试 | MainChainIntegrationTest + 动态验证脚本（docs/28 §7） | 4 集成 | 迭代/发布 |
| 构建 | `mvn verify`、`vite build` | 门禁 | CI |
| 代码评审 | GitHub PR Review / Gitee PR | 5 评审 | 合并前 |

### 3.2 CI/CD 流水线接入（.github/workflows/ci.yml 已配置）

```
push/PR → [frontend job] npm install → npm run lint → npm test → npm run build
        → [backend job]  mvn -B verify（= checkstyle:check + spotbugs:check
                                              + jacoco:report + surefire test + package）
        → 上传构建产物（jar + 前端 dist） → 质量门禁全绿才允许合并
```

**门禁规则**（gate 判定）：

| 门禁项 | 阈值 | 失败动作 |
|---|---|---|

## 5. 持续改进闭环（Continuous Improvement Loop）

### 5.1 问题生命周期

```
发现问题 ──→ 登记（编号） ──→ 分级（P0/P1/P2） ──→ 分配（责任人）
    ↑                                                    │
    │                                                    ↓
 反馈设计/实现 ←── 复检（回归验证） ←── 修复 ──→ 跟踪（状态/时限）
```

### 5.2 问题登记与分类

**登记模板**（沿用 docs/22 §0.4，字段扩展）：

```
| 编号 | 发现日期 | 来源(检查阶段) | 模块/链路 | 级别 | 问题描述 | 根因 | 修复方案 | 责任人 | 状态 | 关闭日期 |
```

**分类体系**：

| 类别 | 子类 | 示例 |
|---|---|---|
| 功能缺陷 | 未实现/错误实现/需求变更 | M-01 满赠未实现（已修） |
| 一致性问题 | 前后端契约/文档失真/双写不一致 | F-01 券字段、L2-03 库存漂移 |
| 安全风险 | 越权/注入/敏感信息 | AD-01 角色断裂、XSS 排查 |
| 性能问题 | N+1/慢查询/缓存失效 | favorites N+1（已修） |
| 代码质量 | 规范/复杂度/死代码 | R-01 死分支 |
| 工程化缺口 | 工具/CI/文档 | BE-02 曝光未落库（已修） |

### 5.3 分配与跟踪

| 角色 | 分配规则 | 跟踪手段 |
|---|---|---|
| 模块负责人 | 按模块归属分配 P1/P2 | 问题登记表状态看板 |
| 迭代负责人 | 兜底 + P0 立即响应 | 每日站会同步 P0/P1 |
| 质量负责人 | 复检确认关闭 | 关闭前回归验证 + 关联测试用例 |

**状态机**：`待处理 → 进行中 → 待复检 → 已关闭 / 已豁免`（豁免需写明理由与期限）。

### 5.4 反馈回设计与实现（形成闭环）

| 反馈通道 | 触发 | 动作 |
|---|---|---|
| **代码级** | 检查发现某类缺陷重复出现（≥3 次同类） | 提炼为 Checkstyle/ESLint 自定义规则或 SpotBugs 过滤规则 → 自动化拦截 |
| **设计级** | 检查发现架构/契约缺陷（如事务内 Redis） | 修订 docs/10/12/16 设计文档 → 更新编码规范 → 全员同步 |
| **流程级** | 某环节漏检（如契约断裂未在 CI 拦截） | 在 CI 增加契约测试/校验步骤 → 提高门禁 |
| **指标级** | 覆盖率下降/缺陷率上升 | 迭代质量报告 → 调整测试策略 → 专项补测 |

**复检机制**：修复后必须**回归验证**（相关单测 + 集成链路），通过后关闭；关闭后进入下轮检查自动覆盖（防复发）。

### 5.5 本方案自身的改进

| 机制 | 说明 |
|---|---|
| 迭代回顾 | 每迭代评审会回顾检查方案执行效果，增删检查项 |
| 基线更新 | 每发布一版，更新 §4 指标基线（如覆盖率从 60% 逐步上调） |
| 工具升级 | 定期升级 checkstyle/spotbugs/eslint/jacoco 版本，同步规则 |
| 模板沉淀 | 每个新模块按 §1.2/§2.3 清单自动套用检查 |

## 6. 关键风险点与应对（R 系列）

| 编号 | 风险 | 应对措施 |
|---|---|---|
| R-01 | 检查流于形式、无人执行 | 强制 CI 门禁（不可绕过）+ 责任人落实到人 + 发布放行矩阵 |
| R-02 | 静态检查误报过多导致免疫 | 定期维护 `spotbugs-exclude.xml`，标注豁免理由；新增规则按类分批引入 |
| R-03 | 覆盖率达标但业务逻辑错误 | 覆盖率是必要非充分条件：强制核心链路 IT + 状态机用例 + 边界 E 系列 |
| R-04 | 文档与代码再次脱节 | 契约测试（coupon.contract.spec 模式）推广到所有接口；文档变更强制走 PR |
| R-05 | 并发/一致性缺陷难以复现 | 关键并发场景（下单/核销/退款）全部接入 IT-07 类压测并保留脚本 |
| R-06 | 遗留 P2 无限积压 | 每迭代固定清理额度（如 ≥3 项），未清理的在迭代报告标注风险 |
| R-07 | 多人协作规范不一致 | pre-commit 钩子 + CI 双保险；新增成员先过"规范速查" |
