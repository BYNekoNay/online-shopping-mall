# 可行性研究报告

> **版本状态**：v0.1 规划版，基于毕业设计任务书编制，尚未与实际代码/审计结果核对，详见 `00-文档说明.md`。

## 1. 引言

### 1.1 编写目的

本报告用于在项目立项阶段，从技术、经济、操作、法律四个维度评估"基于协同过滤算法的智能推荐网络商城"的可行性，作为后续需求分析与系统设计工作的依据。

### 1.2 项目背景

传统 B2C 电商平台普遍采用"千人一面"的商品展示方式，所有用户看到相同的首页推荐与排序，未能结合用户的历史浏览、收藏、购买、评价等行为数据实现个性化展示，导致用户浏览效率低、转化率不高。本项目拟构建一个以"智能推荐"为核心特色的电商平台，融合基于用户的协同过滤（UserCF）与基于物品的协同过滤（ItemCF）算法，实现"猜你喜欢"和"相似商品推荐"，解决"千人一面"问题，提升购物体验与转化率。

### 1.3 参考资料

- 《基于协同过滤算法的智能推荐网络商城的设计与实现》毕业设计任务书（`项目计划书1-AI智能推荐网络商城.md`）
- 任务书所列参考文献 [1]-[10]（协同过滤推荐算法、SpringBoot+Vue3 架构、Redis 缓存优化、MySQL 高并发设计等相关研究）

## 2. 现行方式分析

### 2.1 现行方式

多数中小型电商演示系统或课程设计项目仅实现基础的商品展示、下单、支付流程，商品排序按上架时间或销量固定排序，不具备个性化能力；部分系统即使宣称"智能推荐"，也仅是简单的"热销榜"或人工运营位，未真正基于用户行为数据建模。

### 2.2 存在的问题

1. 商品展示"千人一面"，用户发现感兴趣商品的路径长，浏览转化率低；
2. 缺乏对用户浏览、收藏、购买、评价等行为数据的系统化采集与利用；
3. 搜索能力有限，缺少多维度筛选（分类、价格区间、销量/价格排序）；
4. 商家、管理员端数据统计能力弱，难以支撑运营决策；
5. 高并发场景下（如秒杀、促销）缺乏防超卖、防重复下单等机制。

### 2.3 改进方向

本项目将针对上述问题，引入协同过滤推荐算法体系、多维行为采集与用户画像、智能搜索与筛选、数据看板与统计分析、以及基于 Redis 的高并发库存控制机制。

## 3. 新系统的可行性分析

### 3.1 技术可行性

| 维度 | 分析 |
|---|---|
| 后端框架 | Spring Boot 2.x + MyBatis-Plus 是成熟稳定的 Java 企业级开发组合，社区资料丰富，适合快速构建 RESTful 服务，风险低 |
| 数据库 | MySQL 8.0 支持窗口函数、JSON 字段等特性，满足订单、商品、行为数据的存储与统计查询需求 |
| 缓存 | Redis 可满足热点商品数据、用户行为数据、推荐结果缓存及分布式锁（防超卖）需求，技术方案成熟 |
| 前端 | Vue3 + Element Plus + Axios + ECharts 组合广泛应用于中后台与 B2C 电商前端，学习成本可控 |
| 核心算法 | UserCF/ItemCF 均为经典协同过滤算法，原理清晰（基于余弦相似度），已有大量开源实现与论文（见参考文献 [1][7][8]）可供参考，工程实现难度适中，属于本科毕业设计可完成范围 |
| 鉴权与安全 | JWT 无状态鉴权、BCrypt 密码加密均为业界标准做法，Spring Security/自定义拦截器均可实现 |

**结论：技术方案均基于成熟、可复用的技术栈与经典算法，技术可行性高。** 主要技术风险在于协同过滤算法在数据稀疏（新系统缺乏历史行为数据）情况下的推荐效果，已在任务书"创新点"中提出冷启动优化方案予以应对（见 `05-详细设计说明书.md` §3.4 节）。

### 3.2 经济可行性

- 本项目为本科毕业设计，人力成本为学生个人开发时间投入（16周），无外部人力采购成本；
- 全部技术栈（Spring Boot、MyBatis-Plus、MySQL、Redis、Vue3、Element Plus、ECharts）均为开源免费软件，无授权费用；
- 开发与测试环境可使用个人计算机 + 本地/免费云数据库实例，部署阶段可选用低成本云服务器（如学生优惠云主机）；
- 物流查询若对接"快递100"等第三方 API，通常提供免费测试额度，满足毕业设计演示需求。

**结论：经济投入极低，具备充分的经济可行性。**

### 3.3 操作可行性

- 消费者端复用主流电商交互习惯（分类导航、商品卡片、购物车、订单流程），用户无需额外学习成本；
- 商家端、管理员端采用中后台常见的表格+表单+图表交互模式（Element Plus 组件库），操作门槛低；
- 系统面向 PC 端浏览器访问，响应式设计可兼顾常见分辨率，不需要额外的客户端安装。

**结论：目标用户群体对电商类应用已有普遍认知基础，操作可行性高。**

### 3.4 法律与合规可行性

- 系统仅使用用户在平台内产生的行为数据（浏览、收藏、购买、评价）用于站内个性化推荐，不涉及第三方数据交易；
- 密码等敏感信息采用 BCrypt 加密存储，不明文保存，符合基本的数据安全规范；
- 支付功能采用"模拟支付"（余额/模拟支付宝），不接入真实资金通道，避免触及支付牌照等合规要求；
- 若正式商用还需完善用户隐私政策、数据留存与删除机制，以符合《个人信息保护法》等法规要求（毕业设计阶段作为待办事项记录，见 `02-项目开发计划.md` 风险登记）。

**结论：在毕业设计/演示系统范围内，无法律合规障碍；若未来商用需补充隐私合规工作。**

## 4. 方案比较

| 方案 | 说明 | 优点 | 缺点 | 采纳情况 |
|---|---|---|---|---|
| 方案A：自建协同过滤推荐引擎（UserCF+ItemCF混合） | 任务书指定方案 | 算法透明可控、可结合课程知识深入研究、便于毕业论文论述创新点 | 需要自行实现相似度计算与离线/准实时更新机制，工程量较大 | **采纳** |
| 方案B：固定规则推荐（销量榜/新品榜） | 简单排序规则 | 实现简单、无需行为数据积累 | 无个性化能力，无法解决"千人一面"问题，不满足任务书创新性要求 | 不采纳，仅作为冷启动阶段的兜底策略 |
| 方案C：接入第三方推荐云服务 | 使用商业推荐 SaaS | 开箱即用、效果有保障 | 涉及费用、数据出域、且无法体现毕业设计的算法研究与实现能力 | 不采纳 |

**结论**：采用方案 A（自建 UserCF + ItemCF 混合推荐），并以方案 B 的热门商品推荐作为新用户冷启动的兜底策略，兼顾算法研究深度与工程可实现性。

## 5. 结论与建议

综合技术、经济、操作、法律四个维度分析，本项目具备充分的可行性，建议按任务书确定的技术路线（SpringBoot2.x+MyBatis-Plus+MySQL8.0+Redis+JWT，Vue3+ElementPlus+Axios+ECharts，UserCF/ItemCF混合协同过滤）继续开展需求分析与系统设计工作。需要重点关注的风险点已在 `02-项目开发计划.md` 的风险管理章节列出，并将在开发过程中持续跟踪。
