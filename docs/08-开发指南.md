# 开发指南

> **版本状态**：v0.1 规划版，基于毕业设计任务书及 `03-软件需求规格说明书.md`/`04-概要设计说明书.md`/`05-详细设计说明书.md` 编制，尚未与实际代码核对，详见 `00-文档说明.md`。
>
> **本文档定位**：03/04/05 回答"要做什么"（需求、架构、数据结构、接口契约），本文档回答"怎么做"——具体的工程结构、编码规范、模块开发顺序、前后端并行开发时如何协调，避免与已有文档重复。开发过程中如与本文档冲突，以 03/04/05 的需求与设计为准，本文档随之调整。

## 1. 总体开发流程

### 1.1 分支管理与提交规范

由于是单人开发（见 `02-项目开发计划.md` §2），采用简化但仍规范的 Git 流程：

- `main`：始终保持可运行状态，仅合并已自测通过的功能；
- `dev`：日常开发主线；
- `feature/模块名`（如 `feature/recommend`、`feature/order`）：单个模块或功能点开发用分支，完成并自测后合并回 `dev`；
- 提交信息建议采用 `类型: 简述` 格式（如 `feat: 实现UserCF推荐接口`、`fix: 修复库存预扣减并发问题`），类型包括 `feat/fix/refactor/test/docs/chore`，便于后续生成变更记录、对应 `02-项目开发计划.md` §6 的"版本管理"质量要求。

### 1.2 模块开发总顺序（细化 `02-项目开发计划.md` 第6-12周）

前后端并非"后端全部完成后前端再开始"，而是按**垂直模块**推进：每个模块后端接口基本可用后即冻结接口字段，前端随即介入对接，减少等待。建议顺序（编号对应下文 3.3/4.6 的模块拆分）：

| 顺序 | 模块 | 说明 | 大致对应周次 |
|---|---|---|---|
| 0 | 基础设施 | 统一响应结构、全局异常处理、JWT鉴权、跨域/网关配置、前端请求封装与路由骨架 | 第5-6周 |
| 1 | 用户与鉴权 | 注册/登录、个人信息（FR-C-18） | 第6周 |
| 2 | 商品与分类 | 商品浏览/搜索/筛选/排序（FR-C-01~08）、商家商品管理（FR-M-02~04）、管理员商品审核（FR-A-03~05） | 第6-7周 |
| 3 | 购物车与下单核心链路 | 购物车（FR-C-12/13）、下单/支付/库存扣减（FR-C-14/15、FR-X-04/07）、订单管理（FR-C-16/17、FR-M-05/06/07） | 第7-8周 |
| 4 | 用户行为采集 | 埋点写入 `user_behavior`/`search_history`/`page_view_log`，为推荐与统计模块提供数据基础，需**先于**推荐模块联调 | 第8周 |
| 5 | 推荐算法模块 | UserCF/ItemCF/混合策略/冷启动（FR-C-09/10/11），核心创新点，建议预留充分调试时间 | 第8-9周 |
| 6 | 营销与物流 | 优惠券/促销/积分（FR-X-01~03）、运费模板/物流（FR-M-11、FR-X-05/08） | 第9-10周 |
| 7 | 数据统计模块 | 商家统计（FR-M-08~10）、平台看板与细项统计（FR-A-08/09、FR-S-01~10） | 第10周 |
| 8 | 管理员系统管理 | 用户/商家管理与审核（FR-A-01/02/06/07）、系统参数/日志/字典（FR-A-10~12） | 第10-11周 |
| 9 | 联调收尾与安全自查 | 全链路联调、`06-测试计划.md` 第6节安全自查项 | 第11-12周 |

> **模块3与模块6的依赖说明**：模块3（购物车与下单核心链路）在时序上先于模块6（营销与物流）开发，但 `11-后端开发详细文档.md` §4.1 下单流程步骤4/5在功能上直接调用 `PromotionService.matchActive`、`CouponService.calculateDiscount`、`PointsService.calculateDeduct`/`settleDeduct`/`settleEarn`（均为模块6的服务方法，详见 `11-后端开发详细文档.md` §7）。因此开发模块3时需**提前实现这几个方法的最小可用子集**（能够被 `OrderService.createOrder`/支付回调正确调用即可，不含优惠券/促销的管理员后台CRUD与前端管理页面）；模块6阶段再补齐 `CouponController`/`PromotionController` 的管理端接口与 `13-前端开发详细文档.md` §4 对应的管理员营销管理页面、§2.7 我的优惠券/积分页面等前端部分。

> 之所以把"用户行为采集"单列在推荐算法之前，是因为推荐算法离线计算依赖 `user_behavior` 表已有数据；若两者并行开发，推荐模块开发前期应先用模拟数据（脚本批量插入 `user_behavior`）验证算法正确性，不必等真实埋点上线。

## 2. 后端开发指南

### 2.1 工程结构（Spring Boot 单体，按业务领域分包）

```
backend/
├── src/main/java/com/pzhu/mall/
│   ├── common/            # 统一响应Result、统一异常、分页参数封装、常量、枚举
│   ├── config/            # Spring配置：跨域、JWT拦截器、Redis、MyBatis-Plus、Swagger/Knife4j
│   ├── security/           # JWT工具类、登录拦截器、权限注解与校验切面
│   ├── modules/
│   │   ├── user/          # 用户与鉴权：controller/service/mapper/entity/dto/vo
│   │   ├── product/        # 商品/分类/SKU
│   │   ├── cart/           # 购物车
│   │   ├── order/          # 订单、支付、库存扣减、退款
│   │   ├── behavior/        # 用户行为采集、搜索历史、页面访问日志
│   │   ├── recommend/       # UserCF/ItemCF/混合推荐、缓存写回、定时任务
│   │   ├── marketing/       # 优惠券、促销、积分
│   │   ├── logistics/       # 物流公司、运费模板
│   │   ├── statistics/      # 数据统计聚合查询
│   │   └── admin/          # 商家/用户管理、系统参数、日志、字典
│   └── MallApplication.java
└── src/main/resources/
    ├── application.yml / application-{dev,prod}.yml
    ├── mapper/*.xml         # 复杂统计类SQL放这里，简单CRUD用MyBatis-Plus内置方法
    └── sql/                 # 建表脚本、初始化数据（对应05数据库设计）
```

按业务领域（而非技术分层）作为顶层分包，模块内部再分 `controller/service/service/impl/mapper/entity/dto/vo`，好处是后续如某模块要拆分为独立微服务时改动集中，也便于按 §1.2 的顺序逐模块交付、逐模块提交 PR/自测。

### 2.2 分层职责约定

| 层 | 职责 | 不应做的事 |
|---|---|---|
| Controller | 接收请求、参数校验（`@Valid`）、调用 Service、包装为统一响应 | 不写业务逻辑、不直接操作 Mapper |
| Service / ServiceImpl | 业务规则、事务控制（`@Transactional` 加在此层）、跨模块调用编排 | 不直接拼接 SQL 字符串 |
| Mapper | 数据访问，继承 MyBatis-Plus `BaseMapper`，复杂统计/多表查询用 XML 或 `@Select` | 不承载业务判断逻辑 |
| Entity | 与数据库表一一对应 | 不直接作为接口出入参返回给前端 |
| DTO / VO | DTO 承接请求入参，VO 承接响应出参 | 避免把 Entity 全字段（如密码哈希）暴露给前端 |

统一响应结构与全局异常处理已在 `05-详细设计说明书.md` §5、§7 给出方案，编码时直接落地为 `common.Result<T>` 与 `@RestControllerAdvice` 全局异常处理器，避免各模块各写一套。

### 2.3 关键实现要点索引（避免与05重复，仅给出落地提示）

| 主题 | 实现提示 | 详细设计参照 |
|---|---|---|
| JWT 鉴权 | 登录成功后签发 Token；拦截器统一解析角色并注入到请求上下文（如 `ThreadLocal`），业务代码通过工具类取当前用户，不重复解析 Token | 05 §8 |
| 库存防超卖 | Redisson 或原生 `SETNX`/Lua 脚本实现分布式锁；库存计数用 Redis 字符串或 Hash，避免每次都查库 | 05 §4.2 |
| 推荐算法 | 相似度计算与离线批处理建议用 Spring 定时任务（`@Scheduled`）或轻量任务调度，数据量小时无需引入额外调度中间件 | 05 §3 |
| 订单超时取消 | `@Scheduled` 定时扫描，避免使用死循环轮询；生产级可选延迟队列，毕业设计阶段定时扫描已足够 | 05 §4.5 |
| 运费计算 | 下单确认接口内联调用运费计算工具方法，输入店铺ID+收货地址+订单金额，输出运费，便于单元测试 | 05 §2.3、§4.1 |
| 数据统计 | 高频访问的看板接口避免直接对明细表做实时聚合，参照 04 §6.4 采用定时预计算落汇总表 | 04 §6.4、05 §2.5 |

### 2.4 本地开发环境搭建

1. 安装 JDK 11（版本与依赖版本号统一以 `14-项目脚手架与环境规范.md` §1/§2 为准）、MySQL 8.0、Redis；
2. 执行 `src/main/resources/sql/` 下的建表脚本，导入分类/管理员账号等初始化数据；
3. 复制 `14-项目脚手架与环境规范.md` §3 的 `application.yml` 骨架为 `application-dev.yml`，配置本机数据库、Redis 连接信息（不要将真实密码提交到 Git，用 `.gitignore` 排除或改用环境变量）；
4. IDE 中以 `dev` profile 启动 `MallApplication`，或命令行 `mvn spring-boot:run -Dspring-boot.run.profiles=dev`；
5. 建议引入 Swagger/Knife4j 生成接口文档页面，作为 `09-接口规范.md` 的"活文档"，随开发进度自动更新，减少手工维护接口文档的负担；
6. 每完成一个模块，对照 `06-测试计划.md` 中该模块相关的用例做一次自测，再合并分支。

## 3. 前端开发指南

### 3.1 工程结构

```
frontend/
├── src/
│   ├── api/                # 按后端模块划分的接口封装：user.js/product.js/order.js/recommend.js...
│   ├── views/
│   │   ├── consumer/        # 消费者端页面
│   │   ├── merchant/        # 商家端页面
│   │   └── admin/          # 管理员端页面
│   ├── components/          # 跨端复用组件：分页、图片上传、富文本编辑器、ECharts封装、推荐位卡片
│   ├── router/              # 路由定义 + 基于角色的路由守卫
│   ├── store/               # Pinia：user、cart 等全局状态
│   ├── utils/
│   │   └── request.js        # Axios 实例封装：拦截器、Token注入、错误统一处理
│   └── App.vue / main.js
└── .env.development / .env.production   # 接口 BaseURL 等环境变量
```

### 3.2 三端如何组织

`04-概要设计说明书.md` §3.1 提出"三套前端应用或基于角色的路由与权限动态渲染"两种可能。**单人开发建议采用单一工程 + 角色路由分区**：登录后按 `user.role` 动态加载对应端的路由表（`views/consumer`、`views/merchant`、`views/admin` 三套目录，路由守卫按角色拦截跨端访问），相比维护三个独立工程能显著减少重复的构建配置、公共组件重复实现和维护成本，更适合 16 周的开发周期。若后期确有需要（如三端界面风格差异极大、需要独立部署），可在此基础上按目录拆分为独立工程。

### 3.3 请求封装与统一约定

- Axios 实例在请求拦截器中统一从 Pinia/`localStorage` 读取 Token 并注入 `Authorization` 头；
- 响应拦截器统一解构后端 `Result<T>` 结构（`{code, message, data}`），业务代码直接拿到 `data`，非 `0`/成功码统一走错误提示（Element Plus 的 `ElMessage`）；
- 收到 401（Token 失效）时统一跳转登录页并清空本地登录态，不需要每个页面单独处理。

### 3.4 状态管理与组件规范

- Pinia 按业务域拆 store（`useUserStore`、`useCartStore` 等），避免一个巨大的全局 store；
- 组件命名采用多单词 PascalCase（如 `ProductCard.vue`），跨端复用组件放 `components/` 根目录，仅某一端使用的组件放在对应 `views/{端}/components/` 下；
- 富文本编辑器、图片上传、ECharts 图表统一封装为公共组件，避免在商家发布商品页与管理员详情页各写一份。

### 3.5 前端开发顺序建议

对应 §1.2 的后端交付顺序，前端按同样节奏推进：公共层（请求封装、路由骨架、登录页）→ 商品浏览/搜索/详情 → 购物车/下单/支付页 → 订单列表与用户中心 → 首页/详情页推荐位组件 → 商家端页面 → 管理员端页面。核心链路（浏览-下单-支付）优先打通，符合 `02-项目开发计划.md` §5 中 R2 风险应对措施"优先保证核心链路可运行"的要求。

### 3.6 本地开发环境搭建

1. 安装 Node.js 18 LTS（版本与依赖版本号统一以 `14-项目脚手架与环境规范.md` §4 为准）；
2. `npm install` 安装依赖；
3. 配置 `.env.development` 中的接口 `BaseURL`（如 `http://localhost:8080`，或走下文 4.2 的代理方式）；
4. `npm run dev` 启动本地开发服务器。

## 4. 前后端协调机制

### 4.1 接口契约的唯一来源

`09-接口规范.md` 是前后端联调的接口字段契约唯一来源（`10-数据库规范.md` 是数据库字段的唯一来源）。开发中若某接口的路径、参数或返回字段需要调整，**先改 09（或10），再改代码**（哪怕是单人开发也要保留这个习惯），避免代码与设计文档不一致，也方便毕业论文撰写阶段直接引用作为系统设计依据。

### 4.2 联调方式：代理与跨域

本地联调避免使用浏览器直接跨域请求裸接口，推荐两种方式之一：

- **前端开发服务器代理**：Vite 的 `server.proxy` 配置将 `/api` 前缀转发到后端地址，前端代码始终请求相对路径，切换后端地址只改代理配置；
- **后端统一跨域配置**：在 `config` 层配置 `CorsFilter`/`@CrossOrigin`，允许本地前端开发端口跨域访问。

两者选其一即可，建议优先用代理方式，生产环境走 Nginx 反向代理后二者行为一致（见 `04-概要设计说明书.md` §5 部署架构），减少环境差异导致的联调问题。

### 4.3 并行开发：Mock 先行

按 §1.2 的顺序推进时，某一模块后端尚未完成、前端已想开始页面开发的情况不可避免。约定：

1. 前端按 `09-接口规范.md` 的接口字段结构，用 Mock 工具（如 Vite 插件 `vite-plugin-mock` 或简单的本地 JSON + Axios 拦截）编写与真实接口结构一致的假数据；
2. 后端接口完成并冻结字段后，前端只需删除 Mock 拦截、切回真实请求，不改业务代码，前提是双方都严格遵守 `09-接口规范.md` 定义的字段结构；
3. 若开发中发现 `09-接口规范.md` 定义的字段不够用需要调整，按 §4.1 先改文档、双方对齐后再各自改代码。

### 4.4 联调检查清单

正式联调前，逐项确认以下容易产生分歧的约定，减少联调返工：

| 项目 | 约定 |
|---|---|
| 字段命名风格 | 后端 Java 驼峰、数据库下划线（MyBatis-Plus 自动映射），JSON 出参统一驼峰命名，前后端字段名保持一致 |
| 分页参数 | 请求参数统一为 `pageNum`（页码，从1开始）、`pageSize`；响应统一包含 `total`、`records`/`list` |
| 日期时间格式 | 统一 `yyyy-MM-dd HH:mm:ss`（或 ISO 8601），后端全局 Jackson 配置序列化格式，前端不做额外时区转换 |
| 错误码与提示 | 统一响应结构中的 `code`/`message` 语义提前约定（如 `0` 成功，非 `0` 对应 `common` 层枚举的错误码），前端按 `code` 而非 `message` 文案做逻辑判断 |
| 空值与默认值 | 列表类接口无数据时返回空数组而非 `null`，避免前端渲染报错 |
| 鉴权头 | 统一 `Authorization: Bearer {token}`，前端全局拦截器统一携带，不在业务组件里单独处理 |

### 4.5 环境与配置隔离

后端使用 `application-{dev,test,prod}.yml` 区分不同环境的数据库/Redis连接与密钥；前端使用 `.env.{development,production}` 区分接口 `BaseURL`。真实密码、密钥等敏感配置不提交仓库，通过环境变量或本地未纳入版本控制的配置文件管理，避免 `02-项目开发计划.md` 中提到的密码/密钥泄露风险。
