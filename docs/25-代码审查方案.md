## 第 2 部分 代码审查方案设计（Code Review 流程）

### 2.1 审查流程与节点（3 个强制节点 + 1 个定期节点）

```
┌──────────────────────────────────────────────────────────────────────┐
│                      审查节点总览（Git 工作流）                          │
└──────────────────────────────────────────────────────────────────────┘

[开发中]            [提测前]              [上线前]              [定期]
 写代码即自查   →   PR/MR 强制审查    →   发布门禁检查     →   专项复盘
  (个人)          (≥1 名 Reviewer)     (Release Manager)   (每周/里程碑)
  │                  │                     │                    │
  ├─ 自测通过        ├─ 静态检查通过        ├─ 全量回归通过      ├─ 覆盖率趋势
  ├─ 本地单测        ├─ 单测通过            ├─ 变更清单核对      ├─ 缺陷根因分析
  ├─ 遵循规范        ├─ Reviewer 1+ 审批    ├─ 文档同步核对      ├─ 架构演进评审
  └─ 补测试          └─ 讨论闭环            └─ 回滚预案          └─ 经验沉淀
```

**节点定义与强制要求：**

| 节点 | 触发条件 | 强制动作 | 卡点（不满足则阻塞） |
|---|---|---|---|
| **G1 开发中自查** | 提交代码前 | ①本地单测通过 ②ESLint/Checkstyle 零 error ③自查 Checklist（§2.5）④补测试用例 | 测试失败/静态检查 error 不提交 |
| **G2 提测前 PR 审查** | 合并到 `dev` 分支 | ①≥1 名 Reviewer 批准 ②静态检查 + 单测 + 构建通过 ③前后端契约核对（接口字段一致）④无未关闭评论 | 无批准 / 检查失败 / 契约不一致则禁止合并 |
| **G3 上线前发布门禁** | 合并到 `master`（生产） | ①全量回归通过 ②docs 变更清单核对（§1.4 四项）③回滚预案确认 ④版本标签 | 文档未同步 / 回归失败禁止发版 |
| **G4 定期复盘** | 每周 / 里程碑 | ①覆盖率趋势 ②缺陷根因分类 ③未完善项（§1）进度更新 ④规范/Checklist 迭代 | 里程碑复盘报告缺失 |

### 2.2 前后端审查重点

#### 2.2.1 前端审查重点（Vue 3 + Vite + Element Plus + Pinia）

| 维度 | 审查要点 | 违例示例 |
|---|---|---|
| **组件化** | ①页面是否拆分为可复用组件 ②组件 props/emits 是否显式定义 ③是否避免组件内直接 `localStorage`/`document` 操作 ④v-for 是否绑定 key | 39 视图仅 1 公共组件；组件内散落浏览器 API |
| **状态管理** | ①跨组件共享状态是否入 Pinia（cart/user）②Store 是否直接 import 而非通过 `useStore()` ③页面级临时态不入全局 store ④store action 是否集中处理异步 | 部分页面在组件内 `ref` 复制 store 状态导致失同步 |
| **请求层** | ①API 封装是否统一走 `utils/request` ②错误码处理是否覆盖（10002 跳登录/业务码提示）③loading/错误态是否闭环 ④请求参数是否与后端 DTO 契约一致（F-01 教训） | Confirm.vue 券字段错位导致功能失效 |
| **路由/权限** | ①路由守卫是否校验角色 ②动态菜单与角色一致性 ③页面级权限与接口级权限（RoleCheckAspect）对齐 | 商家端路由与 role=2 匹配 |
| **性能** | ①列表是否分页/虚拟滚动 ②大图是否懒加载 ③是否避免大依赖整包引入（ECharts 按需）④computed 缓存/`v-if` 惰性渲染 ⑤是否避免不必要的响应式嵌套 | 首页 chunk 1.03MB；ECharts 全量引入 |
| **浏览器兼容** | ①browserslist 声明 ②ES 版本（Vite target）③`Array.at`/`Object.hasOwn` 等新 API polyfill ④移动端 375px 基准适配 | 无 browserslist 配置 |
| **安全** | ①`v-html` 使用审查（XSS）②敏感信息不入 localStorage ③图片/链接 URL 校验 ④上传前文件类型/大小预校验 | 用户信息存 localStorage 明文 |

#### 2.2.2 后端审查重点（Spring Boot + MyBatis-Plus + Redis/Redisson）

| 维度 | 审查要点 | 违例示例 |
|---|---|---|
| **接口规范** | ①REST 语义（GET/POST/PUT/DELETE）②统一返回 `Result<T>` ③错误码走 `ErrorCode` 枚举 ④分页结构 `PageResult` ⑤DTO/VO 分离、实体不直接暴露 | 部分接口返回裸实体 |
| **安全性** | ①JWT/角色校验（`@RequireRole`）是否覆盖 ②IDOR 防护（归属校验）③TOCTOU（原子 UPDATE + WHERE）④防超卖（Lua/DB 条件扣减）⑤SQL 注入（LambdaWrapper/预编译）⑥XSS/JSON 解析异常兜底 | H-01~H-22 已修复项回归 |
| **数据库设计** | ①索引覆盖高频查询（orders.user_id/status、order_item.order_id）②N+1 消除 ③大表分页 ④事务边界合理（Redis 操作不入事务）⑤死表/死字段清理（payment 曾死表） | 已修 M-05/AD-04 N+1 |
| **异常处理** | ①业务异常统一 `BusinessException` ②catch 是否吞异常（必须 log.error 带栈）③全局异常兜底 `GlobalExceptionHandler` ④事务回滚语义（rollbackFor） | 已修 O-03/P-05 |
| **并发/幂等** | ①Redis SET NX 幂等键位置（校验后写）②分布式锁（Redisson）使用与释放 ③乐观锁/原子 UPDATE ④重复提交防护 | 已修 O-02/O-08 |
| **性能** | ①慢 SQL 审查（EXPLAIN）②缓存命中率 ③批量查询（selectBatchIds）④异步任务（推荐重算）隔离 ⑤全量扫描告警 | R-03 全量重算待优化 |
| **日志/可观测** | ①关键链路日志（下单/支付/退款/审核）②异常栈完整 ③traceId 贯穿 ④敏感字段脱敏（手机/地址/密码） | 无 traceId |

### 2.3 代码规范与静态检查工具配置建议

#### 2.3.1 前端工具链（建议立即落地）

```jsonc
// package.json 新增 devDependencies
{
  "eslint": "^8.x", "eslint-plugin-vue": "^9.x",
  "@vue/eslint-config-prettier": "^9.x", "prettier": "^3.x",
  "lint-staged": "^15.x", "husky": "^9.x",
  "@vitest/coverage-v8": "^1.x"
}
// scripts
{
  "lint": "eslint . --ext .js,.vue",
  "lint:fix": "eslint . --ext .js,.vue --fix",
  "format": "prettier --write src/",
  "test:coverage": "vitest run --coverage"
}
```

**规则要点**：
- `eslint.config.js`（flat config）：`plugin:vue/vue3-recommended` + `prettier`（格式交给 Prettier，ESLint 只管逻辑）
- `.prettierrc`：`{ "semi": false, "singleQuote": true, "printWidth": 120, "trailingComma": "none" }`
- `.husky/pre-commit`：`npx lint-staged` → `eslint --fix` + `prettier --write` + `vitest run --related`
- `vite.config.js`：`build.target: 'es2020'` + `build.chunkSizeWarningLimit: 600`

#### 2.3.2 后端工具链（建议立即落地）

```xml
<!-- pom.xml 新增 -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-checkstyle-plugin</artifactId>
  <version>3.3.1</version>
  <configuration>
    <configLocation>checkstyle.xml</configLocation>

<plugin>

<plugin>
  <groupId>org.jacoco</groupId>

  <version>0.8.11</version>
  <executions>
    <execution><goals><goal>prepare-agent</goal></goals></execution>
    <execution><id>report</id><phase>verify</phase>
      <goals><goal>report</goal></goals></execution>
  </executions>

```

**checkstyle.xml 规则建议**（最小集）：
- `Indentation`（4 空格）、`LineLength`（120）、`FinalLocalVariable`（可选）
- `AvoidStarImport`、`UnusedImports`、`JavadocMethod`（public 方法）、`MagicNumber`（允许常量）
- `WhitespaceAround`、`NeedBraces`（if/else 必须花括号）
- **规则从严从宽**：error 级仅放格式/导入/命名类；逻辑类交给 SpotBugs

**SpotBugs 关注规则**：`NP_NULL_ON_SOME_PATH`、`EI_EXPOSE_REP`（集合浅拷贝）、`SQL_INJECTION_*`、`DM_CONVERT_CASE`、`URF_UNREAD_FIELD`

### 2.4 审查清单（Checklist）—— 合并 PR 强制项

#### 后端 PR Checklist（PR 模板前置勾选）

```markdown
## 后端 Checklist
- [ ] 本地 `mvn -B verify` 通过（含 checkstyle/spotbugs）
- [ ] 新接口：REST 语义正确、Result/ErrorCode/PageResult 统一、DTO 有校验注解
- [ ] 权限：@RequireRole 覆盖；资源归属校验（IDOR）已加
- [ ] 并发：涉及金额/库存/状态流转用原子 UPDATE + WHERE；幂等键位置正确（校验后写）
- [ ] 事务：@Transactional 边界合理；Redis 操作不入事务；rollbackFor=Exception.class
- [ ] 数据库：无 N+1（批量查询）；新查询走索引；无全表扫描
- [ ] 异常：无裸 catch（必须有 log.error 带栈）；业务异常用 BusinessException
- [ ] 测试：新增用例覆盖正常/边界/异常路径；断言关键状态
```

#### 通用 Checklist（两者共用）

| 维度 | 检查项 |
|---|---|
| 代码质量 | 命名语义化；函数 < 50 行；无复制粘贴代码；无魔法数字（常量化）；无死代码/TODO |
| 可维护性 | 注释解释"为什么"；配置走 application.yml/环境变量；无硬编码（URL/密钥） |

| 可扩展性 | 枚举/策略而非 if-else 堆叠；DTO/VO 与实体隔离 |
| 契约 | 前后端字段名/类型/枚举一致；接口变更同步 docs/09 |

### 2.5 审查人员角色分工与频次

| 角色 | 职责 | 审查频次 |
|---|---|---|
| **作者（Author）** | 提交前自查、补测试、响应评论 | 每次提交 |
| **前端 Reviewer** | 前端代码审查（组件/状态/性能/安全） | 每个 PR ≥1 人 |
| **后端 Reviewer** | 后端代码审查（接口/安全/DB/并发） | 每个 PR ≥1 人 |
| **架构/交叉 Reviewer** | 跨模块改动（order↔marketing↔recommend）、数据库变更、接口契约 | 涉及跨模块/DB 变更时强制 |
| **Release Manager** | G3 发布门禁、版本标签、回滚确认 | 每次发版 |
| **测试人员（QA）** | G2 后冒烟验证、E1~E6 动态验证 | 提测批次 / 发版前 |
| **定期复盘主持人** | G4 复盘、缺陷根因分类、Checklist 迭代 | 每周 / 里程碑 |

> **单人/小团队适配**：当前为个人毕设项目，可收敛为——作者=开发者本人，Reviewer 由"交叉角色"承担：**代码写完后隔夜自审（换视角）+ 对照 Checklist 逐项打勾 + 关键资金/库存/权限改动邀请同学/导师交叉评审**。工具化的静态检查（ESLint/Checkstyle/SpotBugs）是单人场景下"虚拟 Reviewer"，必须强制跑。

| 任务 | 开发者(Author) | Reviewer | QA/验证 | 决策人(用户) | 导师(可选) |

> R=执行，A=负责/审批，C=被咨询，I=知会

### 3.4 问题跟踪与闭环机制

```
问题生命周期：
[发现] → [登记] → [分类定级] → [修复] → [复核] → [关闭/升级]
```

**1. 登记载体**：GitHub Issues（或 Gitee Issues），统一标签：
- 严重度：`sev:p0 阻塞` / `sev:p1 严重` / `sev:p2 一般` / `sev:p3 建议`
- 来源：`src:code-review` / `src:static-analysis` / `src:dynamic-test` / `src:doc-audit`
- 模块：`mod:order` / `mod:marketing` / `mod:recommend` / `mod:frontend` 等

**2. 定级标准**（对齐 docs/22 三级检查）：

| 级别 | 定义 | 处理时限 |
|---|---|---|
| P0 | 数据丢失/资金错误/安全漏洞/主链路完全不可用 | 立即修复（≤24h） |
| P1 | 主链路功能错误/明显契约不一致/越权风险 | 本批次内修复 |
| P2 | 规范/性能/体验/文档问题 | 计划内修复或显式裁剪声明 |

**3. 闭环规则**：
- **修复必须有验证依据**（单测断言/构建通过/动态实测截图），禁止"改了没测"
- Reviewer 关闭评论前必须确认验证依据（沿用 docs/24 的"通过依据"口径）
- 每批次结束跑一次全量回归（`mvn test` + `vitest run` + `vite build`）
- **每周 G4 复盘**：未关闭问题按 P0>P1>P2 排序公示；超期 P1 自动升级给决策人

**4. 与既有流程衔接**：
- 本方案的 Issues 编号挂接 docs/23 修复计划编号（如 `#fix-O-01`），保证可追溯
- docs/24 遗留风险（L2-02 事务内 Redis 归还等）作为已知问题挂入 Issues 跟踪，不重复开题
