# 软件需求规格说明书（SRS）

> **版本状态**：v0.1.2 规划版，基于毕业设计任务书编制，尚未与实际代码/审计结果核对，详见 `00-文档说明.md`。

## 1. 引言

### 1.1 编写目的

本说明书详细定义"智能推荐网络商城"系统的功能性需求与非功能性需求，作为概要设计、详细设计、开发与测试的依据。

### 1.2 术语定义

| 术语 | 说明 |
|---|---|
| UserCF | 基于用户的协同过滤算法（User-based Collaborative Filtering） |
| ItemCF | 基于物品的协同过滤算法（Item-based Collaborative Filtering） |
| GMV | 平台成交总额（Gross Merchandise Volume） |
| 冷启动 | 新用户/新商品缺乏历史行为数据时的推荐难题 |
| SKU | 商品规格单元 |

### 1.3 产品前景

系统面向 B2C 网络购物场景，服务三类角色：消费者、商家、管理员，核心差异化能力为基于协同过滤算法的个性化推荐，替代传统电商"千人一面"的固定排序展示方式。

## 2. 总体描述

### 2.1 产品功能概述

- 消费者：商品浏览、智能搜索、个性化推荐、购物车、下单支付、订单管理、用户中心；
- 商家：店铺管理、商品管理、订单管理、数据统计；
- 管理员：用户管理、商品管理（审核）、商家管理、数据看板、系统管理。

### 2.2 用户特点

| 角色 | 特点 | 核心诉求 |
|---|---|---|
| 消费者 | 数量最多，使用移动/PC浏览器，追求便捷购物体验 | 快速找到感兴趣的商品、简单下单流程 |
| 商家 | 需要高效管理商品与订单 | 提升店铺曝光、便捷的商品/订单/售后管理、经营数据可视化 |
| 管理员 | 平台运营方 | 平台内容合规、商家/用户治理、全局数据洞察 |

### 2.3 假设与约束

- 支付为模拟支付（余额/模拟支付宝），不接入真实支付通道；
- 物流轨迹查询依赖第三方 API（如快递100），可能存在调用频率限制，需设计降级方案；
- 推荐算法效果依赖历史行为数据积累，初期需要冷启动兜底策略；
- 系统面向单体部署架构，暂不考虑分布式微服务拆分（可作为未来扩展）。

## 5. 非功能性需求

| 类别 | 需求描述 |
|---|---|
| 性能 | 商品列表/详情等高频接口在缓存命中情况下响应时间应处于可接受的交互范围；Redis 缓存热门商品、商品详情、推荐结果，降低数据库压力 |
| 安全性 | 密码 BCrypt 加密存储；JWT 鉴权与接口权限校验；XSS 防护（输入过滤、输出编码）；SQL 注入防护（MyBatis-Plus 参数化查询）；CSRF 防护（Token 验证） |
| 可用性 | 全局异常处理器捕获未知异常，避免报错信息直接暴露；关键业务提供友好的错误提示（库存不足、商品下架、优惠券过期等） |
| 高并发 | Redis 分布式锁防止超卖；库存预扣减机制；订单超时自动取消定时任务 |
| 可维护性 | 前后端分离架构，模块化设计，代码遵循统一规范，便于后续扩展（如读写分离、CDN加速等可选项） |
| 兼容性 | 响应式设计，适配 PC 端及常见移动端浏览器分辨率 |
| 数据一致性 | 订单与库存数据一致性保障；支付状态与订单状态同步；操作日志记录便于问题排查 |

## 6. 数据需求（概念数据模型）

系统核心业务实体（详细字段设计见 `05-详细设计说明书.md` 数据库设计章节）：

- 用户（user）、商家/店铺（merchant/shop）、商品（product / sku）、商品分类（category）
- 订单（order）、订单明细（order_item）、购物车（cart）
- 用户行为（user_behavior：浏览/收藏/购买/评价）、用户评分（user_score）、推荐结果缓存（recommend_result）
- 搜索历史（search_history）、页面访问日志（page_view_log，支撑 PV/跳出率/停留时长统计）
- 收货地址（address）、评价（review）
- 优惠券（coupon）、促销活动（promotion）、积分（points）
- 支付记录（payment）、物流信息（logistics）、运费模板（freight_template）
- 操作日志（operation_log）、数据字典（dict）
