## 2. 数据库设计

### 2.1 设计说明

- 存储引擎：InnoDB，字符集：utf8mb4；
- 命名规范：表名/字段名使用小写下划线命名（snake_case）；
- 通用字段：除特别说明外，各表均包含 `id`（主键，bigint，自增）、`create_time`、`update_time`、`is_deleted`（逻辑删除标记）。

### 2.4 用户行为权重设计（支撑评分矩阵构建）

| 行为类型 | 权重建议值 | 说明 |
|---|---|---|
| 浏览 | 1 | 弱兴趣信号 |
| 收藏 | 3 | 中等兴趣信号 |
| 购买 | 5 | 强兴趣信号 |
| 评价（好评） | 4 | 购买后正向反馈，权重叠加或独立计入 |

`user_score.score` 可按用户对同一商品的多次行为加权求和（并可设置衰减/归一化），作为 UserCF/ItemCF 评分矩阵的输入。

### 2.5 数据统计指标计算口径（任务书七.6 / 对应 03 §4.5 FR-S-01~10）

| 指标 | 计算口径 | 数据来源 |
|---|---|---|
| UV / PV | UV = 按 `page_view_log.user_id`（或匿名 `session_id`）去重计数；PV = 记录总条数 | page_view_log |
| 跳出率 | 单次 `session_id` 内仅有 1 条 `page_view_log` 记录（未产生第二次页面跳转）的会话数 / 总会话数 | page_view_log |
| 平均停留时间 | AVG(`leave_time` - `enter_time`)，即 `stay_duration` 均值；`leave_time` 由前端页面卸载/心跳上报 | page_view_log |
| 用户转化漏斗 | 按用户统计各环节达成人数：浏览（user_behavior type=1）→ 加购（cart 表存在记录）→ 下单（order 表存在记录）→ 支付（order.pay_time 不为空），逐层计算转化率 | user_behavior、cart、order |
| 商品浏览量/收藏量 | COUNT(user_behavior) 按 product_id、behavior_type 分组 | user_behavior |
| 商品好评率 | COUNT(review.rating >= 好评阈值，如4分) / COUNT(review) 按 product_id 分组 | review |
| 商品转化率 | COUNT(DISTINCT 下单用户, order_item.product_id) / COUNT(DISTINCT 浏览用户, user_behavior.product_id) | user_behavior、order_item |
| 库存周转率（近似） | 统计周期内 `product.sales` 增量 / 该周期内库存的平均值；毕业设计阶段无逐日库存快照表，采用「周期销量增量 / (期初库存+期末库存)/2」的近似算法，期初/期末库存取周期起止时刻的 `product.stock` 值 | product（周期起止时刻的 stock/sales 快照，可由定时任务落表或日终统计表实现） |
| 用户增长趋势 | 按 `user.create_time` 做日/周/月分组计数 | user |
| 活跃用户 | 统计周期内在 `user_behavior` 或 `order` 中有记录的去重用户数 | user_behavior、order |
| 推荐算法效果（点击率/转化率） | 需在推荐结果曝光与点击处埋点（如新增 `recommend_click_log` 或复用 `page_view_log` 附加来源标记），CTR = 点击数/曝光数，转化率 = 点击后下单数/点击数 | recommend_result 曝光记录 + 点击埋点 |

> 以上口径为毕业设计阶段的可实现简化方案，重点是保证指标"有明确数据来源、可实际计算"，而非工业级精确统计；实现时如发现某项埋点成本过高（如页面级心跳上报），可在测试计划中标注为"部分实现/近似值"并在测试报告中说明。

## 3. 核心算法详细设计

### 3.1 用户-商品评分矩阵构建

```
输入：user_behavior 表全量/增量数据
输出：评分矩阵 R[user][item] = score

for each behavior record (u, i, type, time):
    weight = WEIGHT_TABLE[type]
    R[u][i] += weight * time_decay(time)   # time_decay 可选，越近权重越高
归一化（可选）：对每个用户的评分向量做 min-max 或按最大值归一化，避免活跃用户权重过大
```

### 3.2 基于用户的协同过滤（UserCF）

```
输入：评分矩阵 R，目标用户 u，近邻数 K，推荐数 N
步骤：
1. 计算用户相似度 sim(u, v) = cos(Ru, Rv) = (Ru · Rv) / (||Ru|| * ||Rv||)
   对所有用户对 (u, v) 计算或使用倒排索引优化（仅计算共同交互过商品的用户对，降低复杂度）
2. 取与目标用户 u 相似度最高的 K 个用户，记为邻居集合 N(u)
3. 候选商品集合 = ⋃(v in N(u)) { v 交互过但 u 未交互过的商品 }
4. 对候选商品 i 计算推荐分：
   score(u, i) = Σ(v in N(u)) sim(u,v) * R[v][i]
5. 按 score 降序取前 N 个作为 UserCF 推荐结果
```

### 3.3 基于物品的协同过滤（ItemCF）

```
输入：评分矩阵 R（转置为商品-用户视角），目标用户 u 的历史交互商品集合 H(u)
步骤：
1. 计算商品相似度 sim(i, j) = cos(Ri, Rj)（Ri 为所有用户对商品 i 的评分向量）
   同样可用倒排索引（按用户分组）降低计算量：仅计算同一用户交互过的商品对
2. 对 u 历史交互的每个商品 i in H(u)，取其最相似的 M 个商品
3. 候选商品分值累加：
   score(u, j) = Σ(i in H(u)) sim(i,j) * R[u][i]  ，其中 j 未被 u 交互过
4. 按 score 降序取前 N 个作为 ItemCF 推荐结果（即"相似商品推荐"的基础）
```

### 3.4 混合推荐策略与冷启动

```
混合公式：
final_score(u, i) = α * normalize(userCF_score(u, i)) + (1-α) * normalize(itemCF_score(u, i))

α（UserCF 权重）根据用户活跃度动态调整：
- 用户历史行为数 >= 阈值T_high  → α = 0.6（行为丰富，UserCF 更可靠）
- 用户历史行为数在 [T_low, T_high) → α = 0.4
- 用户历史行为数 < T_low（含新用户） → α = 0，即：
      若历史行为数 == 0（纯新用户）：直接返回"热门商品推荐"（按近N日销量/浏览量排序）兜底
      若历史行为数 较少但非0：以 ItemCF（基于仅有的少量交互）为主，辅以热门商品补足推荐数量
```

### 3.5 推荐结果生成与缓存写回流程

```
定时任务（如每小时/每日触发）：
1. 拉取 user_behavior 增量/全量数据，更新评分矩阵；
2. 计算/更新用户相似度矩阵与商品相似度矩阵（可仅增量更新受影响的用户/商品，降低计算量）；
3. 对活跃用户批量计算 UserCF、ItemCF 推荐结果并按 3.4 节混合；
4. 将结果写入 recommend_result 表 及 Redis 缓存（key: recommend:{userId}，value: 商品ID+分值列表，设置过期时间）；
5. 接口读取推荐结果时：优先读 Redis → 未命中读 recommend_result 表 → 均未命中则返回热门兜底数据。
```

## 4. 关键业务流程详细设计

### 4.1 下单流程

```
1. 消费者选择购物车商品/立即购买商品 → 校验商品状态（是否上架）与库存
2. 选择收货地址 → 生成订单确认页（计算商品金额、优惠券抵扣、运费——运费按订单所属店铺的 `freight_template` 规则匹配收货地址所在区域计算，命中包邮门槛则免运费；店铺未配置模板时按平台默认运费处理，见 FR-X-08）
3. 用户确认下单：
   a. 后端对相关 SKU 执行 Redis 分布式锁 + 库存预扣减（见4.2节）
   b. 预扣减成功后，创建订单（状态=待付款）与订单明细，扣减优惠券/生成积分预记录
   c. 预扣减失败（库存不足）→ 返回"库存不足"提示，下单失败
4. 用户选择支付方式并完成模拟支付 → 支付回调更新订单状态为"待发货"，扣减数据库真实库存，写入支付记录
5. 若用户在超时时间内未支付 → 定时任务将订单置为"已取消"，释放预扣减库存（见4.2节）
```

### 4.2 库存扣减与防超卖流程

```
预扣减阶段（下单时）：
1. 尝试获取 Redis 分布式锁 lock:stock:{skuId}
2. 加锁成功后，读取 Redis 中的库存计数 stock:{skuId}（首次访问时从数据库加载）
3. 若 stock:{skuId} >= 购买数量 → 原子扣减（DECRBY）并释放锁，返回预扣减成功
4. 若库存不足 → 释放锁，返回"库存不足"

支付成功阶段：
5. 数据库中对 product/sku 表执行真实库存扣减（与 Redis 预扣减保持最终一致）
6. 销量字段 +1（用于热销榜/统计）

支付超时/取消阶段：
7. 定时任务扫描超时未支付订单 → 将订单置为"已取消"
8. 归还 Redis 预扣减库存（INCRBY）

发货后：
9. 库存变更仅通过退货流程触发恢复，正常流转中不可逆向增加库存
```

### 4.3 支付回调流程

```
1. 前端发起模拟支付请求 → 后端生成支付记录（状态=支付中）
2. 模拟支付网关（内部模拟或沙箱）异步/同步返回支付结果
3. 后端校验支付回调的合法性（签名/来源校验，模拟环境可简化但需保留校验逻辑设计）
4. 更新支付记录状态为"成功/失败"
5. 支付成功 → 触发订单状态从"待付款"流转为"待发货"，执行4.2节支付成功阶段的库存扣减
6. 支付失败 → 保留订单为"待付款"状态，允许用户重新发起支付（在超时时间内）
```

### 4.4 退款/退货流程

```
1. 消费者在订单详情发起售后申请（退款 或 退货退款），填写原因
2. 商家在订单管理中查看售后申请，审核通过/拒绝
3. 审核通过：
   - 若为"仅退款"：直接调用支付模块执行退款，更新订单状态为"已退款"
   - 若为"退货退款"：等待消费者寄回商品，商家确认收货后再执行退款，恢复库存
4. 审核拒绝：售后申请关闭，订单状态保持不变，记录拒绝原因供消费者查看
```

### 4.5 订单超时自动取消（定时任务设计）

```
定时任务（如每分钟扫描一次）：
SELECT * FROM order WHERE status = 待付款 AND create_time < NOW() - 超时时长(如30分钟)
FOR each 超时订单：
    更新状态为 已取消
    调用4.2节库存释放逻辑归还预扣减库存
    若使用了优惠券 → 释放优惠券占用（恢复为可用状态）
```

## 7. 异常处理设计

- 全局异常处理器（如 Spring 的 `@RestControllerAdvice` 思路）统一捕获业务异常与未知异常，返回统一错误码结构，避免堆栈信息泄露；
- 业务异常分类：库存不足、商品已下架、优惠券已过期/已使用、订单状态非法流转、权限不足等，均定义明确错误码与提示文案；
- 第三方接口（物流查询）调用失败时进行有限次数重试，重试仍失败则降级返回"物流信息暂不可用"提示，不阻塞主流程；
- 数据库连接异常、Redis 连接异常应有降级策略（如 Redis 不可用时，推荐接口降级为热门商品兜底，而非直接报错）。

## 8. 安全设计细化

| 安全项 | 设计方案 |
|---|---|
| 密码存储 | 使用 BCrypt 加盐哈希存储，禁止明文/可逆加密存储密码 |
| 鉴权 | JWT 签发时设置合理过期时间，配合可选的刷新 Token 机制；服务端对关键操作二次校验角色权限 |
| XSS 防护 | 富文本内容（商品详情、评价）存储前进行白名单过滤；前端展示时进行输出编码，避免脚本注入 |
| SQL 注入防护 | 统一通过 MyBatis-Plus 参数化查询/条件构造器，禁止字符串拼接 SQL |
| CSRF 防护 | 关键写操作校验 Token（结合 JWT 无状态特性，CSRF 风险相对较低，但仍建议对表单类请求增加校验） |
| 越权访问防护 | 接口层校验资源归属（如商家只能操作自己店铺的商品/订单，用户只能操作自己的订单/地址） |
| 敏感操作审计 | 管理员的禁用用户、下架商品、审核等操作写入 operation_log，便于事后审计追溯 |

> 以上安全设计将在代码实现后，通过 `06-测试计划.md` 中的"代码审计与安全测试"章节进行实际验证，验证结果与本节设计的差异将回填至本文档 v1.0。
