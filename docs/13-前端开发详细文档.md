# 前端开发详细文档

> **版本状态**：v0.1 规划版，基于毕业设计任务书编制，尚未与实际代码核对，详见 `00-文档说明.md`。
>
> **本文档定位**：`08-开发指南.md` §3 给出的是前端工程的总体结构、三端组织方式与开发顺序；本文档在其基础上进一步下钻到**每个页面/组件的实现要点与关键代码结构**，是编码阶段可直接对照的实现细则。接口字段以 `09-接口规范.md` 为准，与后端的协调机制见 `08-开发指南.md` §4，后端对应实现见 `11-后端开发详细文档.md`。

## 1. 基础设施详细设计

基础设施先于三端具体页面开发（对应 `08-开发指南.md` §1.2 顺序0），后续页面直接复用。

### 1.1 请求封装（`utils/request.js`）

```js
import axios from 'axios'
import { ElMessage } from 'element-plus'
import router from '@/router'
import { useUserStore } from '@/store/user'

const service = axios.create({ baseURL: '/api', timeout: 10000 })

service.interceptors.request.use((config) => {
  const { token } = useUserStore()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

service.interceptors.response.use(
  (response) => {
    const { code, message, data } = response.data
    if (code !== 0) {
      ElMessage.error(message || '请求失败')
      return Promise.reject(new Error(message))
    }
    return data   // 业务代码直接拿到data，无需再解一层.data
  },
  (error) => {
    if (error.response?.status === 401) {
      useUserStore().logout()
      router.push('/login')
    } else if (error.response?.status === 403) {
      router.push('/403')
    } else {
      ElMessage.error('网络异常，请稍后重试')
    }
    return Promise.reject(error)
  }
)

export default service
```

- 对应 `09-接口规范.md` §1.2/§1.4 的统一响应结构与状态码约定：业务失败（`code≠0`）在拦截器内统一弹提示，调用方无需每处 `try/catch`；`401`/`403` 的处理集中在此，页面组件不单独处理；
- `api/` 目录按后端模块拆分文件（`user.js`/`product.js`/`order.js`/`recommend.js`/`merchant.js`/`admin.js`），每个方法直接返回 `service.get/post(...)` 的 Promise，页面中 `await` 调用，不在各页面里拼路径。

### 1.2 路由与权限守卫（`router/index.js` + `router/guard.js`）

```js
const routes = [
  { path: '/login', component: () => import('@/views/common/Login.vue') },
  {
    path: '/', component: () => import('@/layouts/ConsumerLayout.vue'),
    children: [
      { path: '', component: () => import('@/views/consumer/home/Index.vue') },
      { path: 'product/:id', component: () => import('@/views/consumer/product/Detail.vue') },
      { path: 'cart', component: () => import('@/views/consumer/cart/Index.vue'), meta: { requiresAuth: true } },
      // ...
    ],
  },
  {
    path: '/merchant', component: () => import('@/layouts/MerchantLayout.vue'),
    meta: { requiresAuth: true, roles: [2] },
    children: [ /* views/merchant/** */ ],
  },
  {
    path: '/admin', component: () => import('@/layouts/AdminLayout.vue'),
    meta: { requiresAuth: true, roles: [3] },
    children: [ /* views/admin/** */ ],
  },
]

router.beforeEach((to, from, next) => {
  const userStore = useUserStore()
  if (to.meta.requiresAuth && !userStore.token) {
    next({ path: '/login', query: { redirect: to.fullPath } })
  } else if (to.meta.roles && !to.meta.roles.includes(userStore.role)) {
    next('/403')
  } else {
    next()
  }
})
```

- 三端路由表分别定义在 `router/modules/consumer.js`/`merchant.js`/`admin.js` 中再合并导出，对应 `08-开发指南.md` §3.2 的"单一工程 + 角色路由分区"方案；
- 所有路由组件使用动态 `import()` 懒加载，避免首屏一次性加载三端全部代码（见 §10 性能优化）。

### 1.3 状态管理（Pinia）

```
store/
├── user.js       # token、userId、role、nickname；login()/logout()/fetchProfile()
├── cart.js       # 购物车列表、合计金额、selectedCount；fetchList()/updateItem()/removeItem()
├── merchant.js   # 商家端店铺审核状态：shopStatus、rejectReason；fetchApplyStatus()，见 §3.0
├── app.js        # 全局UI状态：加载中、当前激活的分类等（非必须，按需拆分）
```

- `store/user.js` 的 `token` 持久化到 `localStorage`（页面刷新后从中恢复，不重新登录），`logout()` 同时清空 store 与 `localStorage`；
- `store/cart.js` 在购物车页与"加入购物车"操作后主动 `fetchList()` 刷新，不做全局轮询，减少不必要请求。

## 2. 消费者端页面详细设计

对应 `08-开发指南.md` §3.5 的开发顺序：公共层 → 商品浏览 → 购物车/下单 → 订单/用户中心 → 推荐位。

### 2.1 首页（`views/consumer/home/Index.vue`）

- 结构：Banner 轮播（读 `shop`/运营配置，毕业设计阶段可先写死或走简单接口）→ 分类导航（`GET /api/admin/categories` 只读部分）→ "猜你喜欢"推荐位（复用 §5 的 `RecommendList` 组件）→ 商品瀑布流/网格；
- 商品网格分页加载使用"加载更多"或滚动到底部触发下一页（`IntersectionObserver` 监听底部哨兵元素），而非传统分页器，更符合电商首页交互习惯。

### 2.2 分类页与搜索结果页（`views/consumer/category/Index.vue`、`views/consumer/search/Index.vue`）

- 两者共用同一个"商品列表+筛选+排序"组件（`components/ProductListPanel.vue`），差异仅在于请求参数（`categoryId` 或 `keyword`），避免重复实现分页/筛选/排序逻辑；
- 筛选条件（价格区间、排序方式）变化时重置页码为1并重新请求，使用 `watch` 监听筛选条件对象，避免手动在每个筛选控件的 `@change` 里重复调用请求方法；
- 搜索框输入建议做防抖（`lodash-es` 的 `debounce`，300ms）用于"搜索联想词"场景（如有），实际关键词搜索仍以用户点击搜索或回车触发，不对搜索请求本身做防抖。

### 2.3 商品详情页（`views/consumer/product/Detail.vue`）

- 多图轮播使用 Element Plus 的 `el-carousel` 或图片查看器组件；
- SKU 选择器：`skuList` 中每个 SKU 的 `specJson` 解析为"颜色/尺码"等维度选项，用户选择完整规格组合后，前端在 `skuList` 中查找匹配项得到对应 `price`/`stock`，未选满规格前"加入购物车"按钮禁用；该匹配逻辑封装为独立函数 `matchSku(skuList, selectedSpec)`，便于单元测试（见 §11）；
- 商品详情响应中的 `activePromotion` 非空时，在价格区域展示促销标签，标签文案按 `type` 渲染（`type=1` 限时折扣显示"X折"、`type=2` 满减显示"满X减Y"取 `tiers` 中门槛最低档、`type=3` 满赠显示"满X元赠XX"、`type=4` 组合套餐显示"套餐价X元"），渲染逻辑封装为纯函数 `formatPromotionTag(promotion)`，无需请求单独接口；
- 页面底部"相似商品推荐"复用 `RecommendList` 组件，`mode="similar"`，传入当前 `productId`；
- 页面进入/离开时机是 `page_view_log` 埋点的上报点，见 §7。

### 2.4 购物车页（`views/consumer/cart/Index.vue`）

- 数量修改、选中状态切换均为"乐观更新"：先更新本地 `store/cart.js` 中的数据立即反映到UI，同时发起接口请求，请求失败再回滚本地状态并提示，避免每次操作都等待接口响应造成的卡顿感；
- 合计金额在前端本地根据 `selected=true` 的行实时计算展示（不必等接口返回），下单时的最终金额仍以后端 `POST /api/orders` 响应为准，前端展示值仅供参考。

### 2.5 订单确认页与支付页（`views/consumer/order/Confirm.vue`、`Pay.vue`）

- 确认页调用后端生成订单前的"预览"（如无独立预览接口，可直接用 §2.4 的本地合计 + 简化的本地运费预估展示，真正运费以提交订单后端返回为准，避免前端重复实现 `10-数据库规范.md` `freight_template` 的完整匹配规则）；确认页需**按购物车行的 `shopId` 分组展示**（即使最终是否拆单以后端返回为准，前端提前分组展示能让用户清楚"这是几笔订单"）；
- 优惠券选择：调用 `GET /api/user/coupons?status=0`（`0` 表示未使用/可用，见 `10-数据库规范.md` `user_coupon.status` 定义）供用户选择，选中的 `couponId` 随提交请求传递；积分抵扣：调用 `GET /api/user/points` 展示当前余额与"可抵扣约X元"（前端按 `09-接口规范.md` §2.4 `usePoints` 规则本地估算 `min(points/100, goodsAmount*0.5)` 仅供展示，不用于校验），提供一个"使用积分抵扣"开关，勾选后随请求传 `usePoints:true`；两者均为**分组级別展示提示**——优惠券按其归属店铺仅对匹配分组的小计生效，积分固定仅对分组数组第一组生效（对应 `09-接口规范.md` §2.4 说明），提交前在确认页对应分组旁标注"积分仅抵扣本笔订单"提示文案；
- 提交订单前**生成 `requestId`（如 `uuid`）**随请求发送，对应 `09-接口规范.md` §1.5 的幂等约定，防止用户重复点击"提交订单"按钮导致重复下单——按钮本身也需在请求发出后立即禁用（`loading` 状态），双重防护；
- `POST /api/orders` 响应 `data` 为**订单数组**（对应 `09-接口规范.md` §2.4 跨店铺拆单设计），前端需按数组长度分情况处理：
  - 数组长度为1（未拆单或单店铺下单）：直接跳转该订单的支付页 `Pay.vue`；
  - 数组长度大于1（跨店铺拆单）：跳转一个"分批支付"列表页，展示每个子订单的店铺名/金额与支付状态，用户逐个点击进入 `Pay.vue` 完成支付，全部支付完成或用户主动退出后返回订单列表；
  - 数组长度小于提交时的店铺分组数（部分店铺下单失败）：提示"部分商品下单失败，已为您创建其余订单"，同样进入上述分批支付流程处理已成功创建的订单；
- 支付页展示订单金额与支付方式单选，调用 `POST /api/orders/{id}/pay` 后跳转订单详情页；分批支付场景下，单个子订单支付完成后返回分批支付列表页而非订单列表，直到全部子订单处理完毕。

### 2.6 订单列表与详情（`views/consumer/order/List.vue`、`Detail.vue`）

- 列表按状态 Tab 切换（全部/待付款/待发货/已发货/已完成/已取消），每个 Tab 对应 `status` 查询参数，切换 Tab 时重置分页；
- 详情页按订单状态动态展示可执行操作按钮（取消/继续支付/确认收货/申请售后/评价），状态到按钮的映射维护为一个纯函数 `getAvailableActions(orderStatus)`，避免模板中堆砌 `v-if` 判断；
- 明细行 `items` 中 `isGift=true` 的赠品行（来自满赠促销，见 `09-接口规范.md` §2.4/`10-数据库规范.md` §2.4.2）在列表/详情中渲染为独立的"赠品"标签而非 `¥0.00` 金额，且不展示"申请售后""评价"等针对该行的操作入口（赠品仅随整单售后处理，见 `11-后端开发详细文档.md` §4.6）。

### 2.7 用户中心（`views/consumer/user/*.vue`）

- 个人信息、收货地址管理为标准表单+列表 CRUD；
- 收藏夹、浏览历史页面调用同一套"用户行为查询"接口按 `behaviorType` 区分（对应 `05-详细设计说明书.md` §2.3 的说明：这两个页面复用 `user_behavior` 表，不是独立数据源），前端只需关注展示，不关心后端存储细节；
- 我的优惠券页面（`Coupons.vue`）：Tab 切换未使用/已使用/已过期（对应 `GET /api/user/coupons` 的 `status` 参数），列表项展示券面额/门槛文案（按 `discountRule.mode` 区分"满X减Y"/"满X享Y折"）；
- 我的积分页面（`Points.vue`）：顶部展示 `GET /api/user/points` 的当前余额，下方为 `GET /api/user/points/records` 的分页流水列表（展示 `changeAmount` 正负、`type` 对应文案"下单获得"/"订单抵扣"、`createTime`），本项目暂不提供积分兑换入口（对应 `10-数据库规范.md` §2.4.3 `type=3` 暂不实现下单入口的说明），页面不出现"去兑换"按钮。

## 3. 商家端页面详细设计

### 3.0 商家入驻申请（`views/merchant/apply/Apply.vue`）与路由守卫

- 商家角色（`role=2`）登录后进入 `/merchant` 路由时，路由守卫（`router/guard.js`，扩展 §1.2 的 `beforeEach`）先调用 `GET /api/merchant/shop/apply-status`：
  - `hasApplied=false` 或 `status=2`（已拒绝）→ 重定向至 `/merchant/apply`，展示 `Apply.vue` 入驻申请表单（已拒绝时额外展示 `rejectReason` 并允许重新提交，对应 `09-接口规范.md` §2.5 `POST /api/merchant/shop/apply` 的"拒绝后重新提交"语义）；
  - `status=0`（待审核）→ 重定向至 `/merchant/apply-pending`，展示"申请审核中，请耐心等待"的静态提示页，不展示表单；
  - `status=1`（正常）→ 放行进入正常的店铺管理/商品/订单等商家页面；
  - `status=3`（已禁用）→ 重定向至一个"店铺已被禁用"的提示页（复用 `apply-pending` 页面按 `status` 传参切换文案，不必新建页面）；
  - 该状态查询结果缓存于 `store/merchant.js`（新增，字段 `shopStatus`/`rejectReason`），避免商家端每次路由跳转都重复请求，仅在首次进入 `/merchant` 或用户主动提交申请后刷新；
- `Apply.vue` 表单字段：`name`、`contactName`、`contactPhone`、`licenseNo`、`licenseImage`（走 `POST /api/upload/image` 上传后取URL回填）、`applyReason`（选填），提交调用 `POST /api/merchant/shop/apply`，成功后更新 `store/merchant.js` 状态并重定向至 `/merchant/apply-pending`。

### 3.1 店铺管理（`views/merchant/shop/Info.vue`、`Decoration.vue`、`Freight.vue`）

- 以下三个页面均要求 `store/merchant.js` 中 `shopStatus=1`（已由 §3.0 的路由守卫保证），页面内部无需再各自判断店铺审核状态；
- 店铺装修页（`Decoration.vue`）：拖拽式楼层布局对毕业设计而言复杂度过高，建议简化为"表单配置banner图列表+楼层区块的顺序"，保存为 `decorationConfig` JSON 结构直接提交，不实现真正的可视化拖拽编辑器；
- 运费模板页（`Freight.vue`）：表单支持添加多条"区域-运费"规则（对应 `10-数据库规范.md` `freight_template.region_rule_json`）+ 包邮门槛开关，区域选择使用**固定的8个大区下拉单选**（华东/华南/华北/华中/西南/西北/东北/港澳台，见 `10-数据库规范.md` §2.2.1，不是省份多选——一条规则对应一个大区的统一运费），规则列表本地维护为数组，提交时序列化为 JSON；收货地址表单（§2.7）中的省份下拉选项固定使用 `10-数据库规范.md` §2.2.1 表格中的省份全称列表，保证前端提交的 `province` 值能与后端大区映射精确匹配；

### 3.2 商品管理（`views/merchant/product/List.vue`、`Edit.vue`）

- 商品发布/编辑页富文本详情使用 wangEditor 或 TinyMCE 等 Vue3 兼容的富文本组件，图片上传统一走 `POST /api/upload/image`（见 `09-接口规范.md` §1.6）；
- SKU 编辑采用"规格维度+规格值"动态添加 UI（如添加"颜色"维度、录入"红/黄/蓝"值），前端做笛卡尔积生成 SKU 组合表格供逐条填写价格/库存，生成逻辑封装为纯函数 `generateSkuCombinations(specs)`；
- 列表页批量操作（批量上下架）通过表格多选 + 底部悬浮操作栏实现，调用 `PUT /api/merchant/products/batch`。

### 3.3 订单与售后（`views/merchant/order/List.vue`、`Ship.vue`、`Refund.vue`）

- 发货表单：物流公司下拉（读 `dict` 表 `LOGISTICS_COMPANY` 类型的字典项）+ 物流单号输入；
- 售后审核页：展示消费者申请原因与凭证图片，审核通过/拒绝两个操作按钮，通过时二次确认弹窗（涉及资金退款，避免误触）。

### 3.4 数据统计看板（`views/merchant/statistics/Dashboard.vue`）

- 见 §8 ECharts 封装约定；核心图表：销售趋势折线图（日/周/月切换）、热销 TOP10 柱状图；顶部卡片展示销售总额/订单量等汇总数字。

## 4. 管理员端页面详细设计

- 用户管理、商品审核、商家审核均为"列表+筛选+详情弹窗/抽屉+操作按钮"的标准管理后台模式，可复用同一套 `components/DataTable.vue`（封装分页表格的通用交互：加载态、空态、分页器联动）减少重复代码；
- 营销管理（`views/admin/marketing/Coupons.vue`、`Promotions.vue`，对应 FR-X-02）：优惠券/促销活动均为平台运营统一配置（`coupon`/`promotion` 表未设计商家归属字段，见 `09-接口规范.md` §3），列表+新建/编辑表单+下线操作，表单内 `discountRule`/`ruleJson` 按 `10-数据库规范.md` §2.4.1/§2.4.2 的结构动态渲染（如新建促销时先选 `type`，再展示对应 `type` 的子表单字段，逻辑封装为纯函数 `getPromotionRuleFields(type)`）；
- 数据看板（`views/admin/dashboard/Index.vue`）：GMV/用户增长趋势/转化漏斗/推荐算法效果四类图表，转化漏斗使用 ECharts 的漏斗图类型直观展示"浏览→加购→下单→支付"的逐层转化（对应 `03-软件需求规格说明书.md` FR-S-04）；
- 系统管理（参数配置/操作日志/数据字典）优先级最低，按 `08-开发指南.md` §1.2 顺序排在最后开发。

## 5. 推荐位组件（`components/RecommendList.vue`）

```vue
<script setup>
const props = defineProps({
  mode: { type: String, default: 'guess' },   // guess | similar
  productId: { type: [String, Number], default: null },
})
const list = ref([])
onMounted(async () => {
  list.value = props.mode === 'similar'
    ? await getSimilarProducts(props.productId)
    : await getGuessYouLike()
})
</script>
```

- 该组件在首页（`mode="guess"`）与商品详情页（`mode="similar"`）复用，对应 `09-接口规范.md` §2.2 的两个推荐接口；
- 未登录用户调用"猜你喜欢"接口时，后端已按 `12-核心算法设计文档.md` §8 返回热门兜底结果，前端**无需区分登录态做特殊处理**，始终按同一套 UI 展示返回列表即可；
- 推荐位的曝光埋点（用于 `12-核心算法设计文档.md` §10.2 的 CTR 计算）在组件 `mounted` 且列表非空时上报一次"曝光"事件，点击列表项时跳转详情页并携带来源标记（如查询参数 `?from=recommend`），供后端统计点击来源。

## 6. 组件与页面规范

- 组件命名多单词 PascalCase，Props 使用 `defineProps` 显式声明类型与默认值，避免隐式 `any`；
- 跨端复用组件（`Pagination`/`ImageUpload`/`RichTextEditor`/`RecommendList`/`DataTable`）放 `components/` 根目录；仅某一端使用的组件放对应 `views/{端}/components/` 下，不放全局目录污染其他端的可见范围；
- 表单校验统一使用 Element Plus 的 `el-form` + `rules`，校验规则集中定义在页面同目录下的 `rules.js`，避免和模板混在一起。

## 7. 埋点上报实现

- 除 `page_view_log` 外的行为埋点（浏览/收藏/购买/评价）**由后端业务接口在处理对应请求时自动记录**（见 `11-后端开发详细文档.md` §5），前端只需正常调用业务接口（如查看详情、收藏、下单），**不需要单独调用埋点接口**，避免前后端各记一遍导致数据不一致；
- 仅 `page_view_log` 需要前端主动上报：路由守卫 `afterEach` 中记录 `enterTime` 并调用创建接口拿到记录 `id`；页面卸载（`onBeforeUnmount`）或路由离开时调用 `PUT /api/behavior/page-view/{id}/leave` 回填 `leaveTime`；浏览器标签关闭场景使用 `navigator.sendBeacon` 而非普通 `axios` 请求，保证页面卸载过程中请求仍能可靠发出。

## 8. ECharts 封装（`components/EchartsWrapper.vue`）

```vue
<script setup>
const props = defineProps({ option: Object })
const chartRef = ref(null)
let chart
onMounted(() => {
  chart = echarts.init(chartRef.value)
  chart.setOption(props.option)
  window.addEventListener('resize', chart.resize)
})
watch(() => props.option, (val) => chart?.setOption(val))
onBeforeUnmount(() => {
  window.removeEventListener('resize', chart.resize)
  chart?.dispose()
})
</script>
<template><div ref="chartRef" style="width:100%;height:100%" /></template>
```

- 商家端销售趋势/热销榜、管理员端 GMV/转化漏斗/推荐效果看板均基于此组件传入不同 `option`，不重复写 `echarts.init`/`resize`/`dispose` 的生命周期代码；
- 折线图（趋势）、柱状图（TOP10排行）、漏斗图（转化率）、饼图（如需占比展示）的 `option` 生成逻辑各自封装为纯函数（如 `buildTrendOption(data)`），便于复用与测试。

## 9. 性能优化要点

- 路由组件懒加载（见 §1.2），减少首屏 JS 体积；
- 商品图片使用 `loading="lazy"` 原生懒加载或 Element Plus `el-image` 的 `lazy` 属性，列表页图片不一次性全部加载；
- 搜索框、筛选联动等高频触发场景使用防抖（输入类）/节流（滚动类），避免请求风暴；
- 商品列表如出现长列表卡顿，可引入虚拟滚动（如 `vue-virtual-scroller`）作为可选优化项，非首期必做。

## 10. 单元测试规范

- 使用 Vitest + `@vue/test-utils`；
- 优先覆盖有明确输入输出、不依赖真实接口的纯函数：`matchSku`（§2.3）、`generateSkuCombinations`（§3.2）、`getAvailableActions`（§2.6）、运费/合计金额的本地计算函数；
- 组件级测试优先覆盖交互复杂的组件（SKU 选择器、购物车行编辑、`RecommendList`），Mock `api/` 层返回数据而非真实请求后端。
