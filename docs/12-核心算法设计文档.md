## 1. 概述

系统的核心创新点是"UserCF + ItemCF 混合协同过滤推荐"，替代传统电商固定排序/人工运营位的"千人一面"展示方式。本文档设计的算法围绕四个环节展开，对应 `00-文档说明.md` §3 创新点对照表：

1. 用户-商品评分矩阵构建（数据准备，见 §3）；
2. UserCF 与 ItemCF 两种协同过滤算法（见 §4、§5）；
3. 基于用户活跃度的混合加权策略与冷启动兜底（对应创新点①③，见 §7、§8）；
4. 结果的准实时缓存更新（对应创新点④，见 §9）。

## 2. 问题定义与符号说明

| 符号 | 含义 |
|---|---|
| $U = \{u_1, u_2, ..., u_m\}$ | 用户集合，$m$ 为用户数 |
| $I = \{i_1, i_2, ..., i_n\}$ | 商品集合，$n$ 为商品数 |
| $R \in \mathbb{R}^{m \times n}$ | 用户-商品评分矩阵，$R_{u,i}$ 表示用户 $u$ 对商品 $i$ 的兴趣分值 |
| $N(u)$ | 用户 $u$ 的 K 近邻用户集合（UserCF） |
| $S(i)$ | 与商品 $i$ 最相似的 M 个商品集合（ItemCF） |
| $H(u)$ | 用户 $u$ 历史交互过的商品集合 |
| $sim(x, y)$ | 余弦相似度函数 |

推荐问题形式化为：给定评分矩阵 $R$ 与目标用户 $u$，为其生成一个 Top-N 商品排序列表，使得列表中商品与用户真实兴趣的匹配程度最大化。

## 3. 用户-商品评分矩阵构建（数据准备）

### 3.1 行为权重设计

| 行为类型 | 权重 $w$ | 设计依据 |
|---|---|---|
| 浏览 | 1 | 弱兴趣信号，用户可能仅路过 |
| 收藏 | 3 | 中等强度信号，体现明确的持续关注意愿 |
| 购买 | 5 | 最强信号，已发生实际消费决策 |
| 评价（好评，rating≥4） | 4 | 购买后的正向反馈，强化对该商品的兴趣确认 |

权重比例（1:3:5:4）参考电商推荐系统常见的行为强度设计经验，核心原则是"行为转化成本越高、越能反映真实偏好，权重越大"。

### 3.2 时间衰减

行为发生时间越久，对当前兴趣的代表性越弱，引入指数衰减：

$$decay(t) = e^{-\lambda (t_{now} - t)}$$

- $t$ 为行为发生时间，$t_{now}$ 为当前计算时刻，单位为天；
- $\lambda$ 为衰减系数，建议初始取值 $\lambda = 0.05$（约14天后权重衰减至约50%），毕业设计阶段可作为可调参数，在测试中观察不同 $\lambda$ 对推荐结果新鲜度的影响并记录在测试报告中。

### 3.3 评分矩阵构建算法

```
输入：user_behavior 表全量/增量记录
输出：评分矩阵 R（稀疏矩阵，仅存储非零项）

初始化 R 为空的稀疏矩阵（Map<userId, Map<productId, Double>>）
for each behavior record (u, i, type, t):
    w = WEIGHT_TABLE[type]
    R[u][i] = R[u][i] (若不存在则为0) + w * decay(t)

归一化（每个用户独立做 min-max 归一化，避免"活跃用户对所有商品评分普遍偏高"扭曲相似度计算）：
for each user u:
    max_score = max(R[u])
    if max_score > 0:
        for each i in R[u]:
            R[u][i] = R[u][i] / max_score
```

> 稀疏存储是必须的：$m \times n$ 的稠密矩阵在商品量稍大时即不可行（如1万用户×1万商品=1亿单元格），而用户实际交互过的商品通常只占极小比例，使用 `Map<Long, Map<Long, Double>>` 或数据库 `user_score` 表按需加载即可。

## 4. 基于用户的协同过滤（UserCF）详细设计

### 4.1 相似度计算

用户 $u$、$v$ 的余弦相似度：

$$sim(u, v) = \frac{R_u \cdot R_v}{\|R_u\| \times \|R_v\|} = \frac{\sum_{i \in I} R_{u,i} R_{v,i}}{\sqrt{\sum_{i \in I} R_{u,i}^2} \times \sqrt{\sum_{i \in I} R_{v,i}^2}}$$

直接两两计算所有用户对的复杂度为 $O(m^2 n)$，当 $m$（用户数）增长时不可行，需用倒排索引优化：

```
输入：评分矩阵 R
输出：用户相似度矩阵（仅保留有共同交互商品的用户对）

第一步：构建"商品→交互过该商品的用户列表"倒排索引
item_users = {}
for each user u, item i in R:
    item_users[i].append(u)

第二步：仅对有共同商品的用户对累加内积（避免枚举所有 m² 用户对）
co_rate = {}  # co_rate[u][v] 累加交集贡献
for each item i, users_of_i in item_users:
    for u in users_of_i:
        for v in users_of_i:
            if u != v:
                co_rate[u][v] += R[u][i] * R[v][i]

第三步：结合各用户评分向量的模长，计算最终余弦相似度
for each (u, v) in co_rate:
    sim(u, v) = co_rate[u][v] / (norm[u] * norm[v])
```

复杂度由 $O(m^2 n)$ 降至 $O(\sum_i |item\_users_i|^2)$，实际数据中每件商品的交互用户数远小于总用户数 $m$，因此该优化在数据规模变大后收益显著。

### 4.2 近邻选择与推荐分计算

1. 对目标用户 $u$，取 $sim(u, v)$ 降序前 $K$ 个用户构成 $N(u)$（$K$ 建议初始取值 20，作为可调超参数）；
2. 候选商品集合为 $\bigcup_{v \in N(u)} \{i \mid i \in H(v), i \notin H(u)\}$；
3. 候选商品 $i$ 的推荐分：

$$score_{UserCF}(u, i) = \sum_{v \in N(u)} sim(u,v) \times R_{v,i}$$

4. 按 $score$ 降序取前 $N$ 个（$N$ 为需要展示的推荐数量，如10个）。

### 4.3 复杂度小结

- 相似度计算（倒排索引优化后）：$O(\sum_i |item\_users_i|^2)$；
- 单用户推荐分计算：$O(K \times \bar{|H(v)|})$，$K$ 为近邻数，$\bar{|H(v)|}$ 为近邻平均交互商品数；
- 整体离线批量计算适合定时任务（如每小时/每日），不适合请求时实时计算，因此推荐结果必须走"离线计算 + 缓存查询"的架构（见 §9）。

## 5. 基于物品的协同过滤（ItemCF）详细设计

### 5.1 商品相似度计算

将评分矩阵转置为"商品-用户"视角，商品 $i$、$j$ 的相似度：

$$sim(i, j) = \frac{\sum_{u \in U} R_{u,i} R_{u,j}}{\sqrt{\sum_{u} R_{u,i}^2} \times \sqrt{\sum_{u} R_{u,j}^2}}$$

同样使用倒排索引优化（按用户分组，仅对同一用户交互过的商品对累加内积），复杂度分析与 §4.1 对称：$O(\sum_u |H(u)|^2)$。

### 5.2 推荐分计算

1. 对目标用户 $u$ 历史交互的每个商品 $i \in H(u)$，取其相似度最高的 $M$ 个商品（$M$ 建议初始取值 10）；
2. 候选商品累加分：

$$score_{ItemCF}(u, j) = \sum_{i \in H(u)} sim(i,j) \times R_{u,i}, \quad j \notin H(u)$$

3. 商品详情页"相似商品推荐"直接复用 $sim(i, \cdot)$ 降序结果（即固定目标商品 $i$，取相似度最高的 $N$ 个商品），不需要用户历史行为参与，这是 ItemCF 相比 UserCF 的额外工程价值——**可用于未登录用户的商品详情页推荐位**。

## 6. 相似度矩阵的存储与工程优化

- 相似度矩阵是计算过程中的**中间结果**，不需要写入 `10-数据库规范.md` 定义的持久化业务表（该规范中的 `user_score`/`recommend_result` 分别是评分矩阵与最终推荐结果，均为必须持久化的数据；相似度矩阵本身用完即可丢弃）；
- 推荐工程实现两种可选存储方式：
  1. **纯内存计算**：定时任务运行期间在内存中构建相似度矩阵（`Map<Long, Map<Long, Double>>`），计算完最终推荐结果后即释放，适合数据规模较小的毕业设计场景，实现最简单；
  2. **Redis Hash 缓存**：`item_sim:{itemId}` 存该商品的 Top-M 相似商品及分值，供"相似商品推荐"接口直接读取（不必每次都重新计算 ItemCF 推荐分），适合希望进一步降低单次推荐计算耗时的场景；
- 毕业设计阶段建议优先选择方式1（纯内存计算 + 仅缓存最终 `recommend_result`/`recommend:{userId}`），降低实现复杂度；若时间允许，可在完成方式1并验证效果后，再实现方式2作为性能优化项，在论文中体现"迭代优化"的过程。

## 7. 混合推荐策略详细设计

### 7.1 归一化

UserCF 与 ItemCF 的原始分值量纲不同（累加求和的分值范围不固定），混合前需分别做 min-max 归一化到 $[0, 1]$：

$$normalize(score_i) = \frac{score_i - \min(scores)}{\max(scores) - \min(scores)}$$

### 7.2 加权混合公式

$$final\_score(u, i) = \alpha \times normalize(score_{UserCF}(u,i)) + (1-\alpha) \times normalize(score_{ItemCF}(u,i))$$

### 7.3 α 的动态调整依据

| 用户历史行为数 $\|H(u)\|$ | α 取值 | 依据 |
|---|---|---|
| $\geq T_{high}$（建议初始值20） | 0.6 | 行为数据充分时，用户间的兴趣共性（UserCF）比商品关联性（ItemCF）更能捕捉个性化差异，故适当提高UserCF权重 |
| $[T_{low}, T_{high})$（$T_{low}$ 建议初始值5） | 0.4 | 行为数据中等，两种信号并重偏向ItemCF，因为少量行为下商品关联比"寻找相似用户"更稳定 |
| $< T_{low}$（含新用户，$=0$） | 0 | 行为过少或为0时UserCF的近邻相似度计算不可靠（相似度计算基于的交集过小甚至为空），完全依赖ItemCF或直接走冷启动 |

$T_{high}$、$T_{low}$、$\alpha$ 的具体取值均为初始建议值，非固定不变——**毕业设计的可验证环节**应当是：准备一批测试用户（划分不同行为数区间），分别用固定 $\alpha$（如 0、0.3、0.5、0.7、1.0）计算推荐结果，人工或按 §10 的离线评估方法比较效果，从而在论文中给出"参数选择的实验依据"而非拍脑袋决定。

## 8. 冷启动策略详细设计

### 8.1 新用户冷启动（本设计范围内的冷启动场景）

$$
recommend(u) = \begin{cases}
HotRank(N) & |H(u)| = 0 \text{（纯新用户）} \\
ItemCF(u, N) \ \cup\ HotRank(N - |ItemCF(u,N)|) & 0 < |H(u)| < T_{low}
\end{cases}
$$

`HotRank`（热门商品排序）计算公式：

$$hot\_score(i) = w_1 \times sales_{recentN}(i) + w_2 \times views_{recentN}(i)$$

- $sales_{recentN}(i)$、$views_{recentN}(i)$ 分别为商品 $i$ 近 N 日（建议7天）销量、浏览量，均先做归一化再加权，避免销量与浏览量量纲差异过大；
- $w_1, w_2$ 建议初始取值 $0.7, 0.3$（销量比浏览量更能反映真实购买意愿）；
- `HotRank` 结果对应 `10-数据库规范.md` `recommend_result.algorithm_type = 4`（热门兜底），可按较低频率（如每日一次）离线计算并全局共享缓存（`hot:products`），不需要按用户区分。

### 8.2 范围说明

任务书与 `05-详细设计说明书.md` 均仅要求"新用户冷启动"，**本设计不引入"新商品冷启动"（如基于商品内容标签的相似推荐）**，避免超出任务书范围；若毕业设计答辩后续有余力扩展，可将商品的 `category_id`/名称关键词作为内容特征，对新商品做基于内容的相似商品匹配，作为可选的加分项而非本设计的必做内容。

## 9. 推荐结果生成与缓存更新（对应创新点④"实时推荐"）

### 9.1 更新触发方式

- **定时批量更新**（主要方式）：`@Scheduled` 定时任务按固定频率（如每小时）对活跃用户（近7日有行为记录）批量重算 §7 的混合推荐结果；
- **准实时触发**（可选增强）：用户发生"购买"这一强信号行为后，可只针对该用户单独触发一次轻量重算（仅重算该用户的 ItemCF 部分，因为新购买直接影响 $H(u)$，而不必等待下一次全量定时任务），实现"准实时"效果，对应任务书"实时推荐"创新点的合理工程诠释（协同过滤算法本身不适合逐请求实时计算，"实时"应理解为"缓存的准实时更新"而非"每次请求都重新计算全量矩阵"）。

### 9.2 缓存写回与读取

```
定时任务批量流程：
1. 更新评分矩阵（§3.3）
2. 计算/更新用户相似度、商品相似度（§4.1、§5.1，可仅增量更新受影响用户/商品）
3. 对活跃用户计算 UserCF、ItemCF 并按 §7 混合，得到 final_score 排序列表
4. 写入 recommend_result 表（algorithm_type=3）与 Redis（key: recommend:{userId}，Sorted Set，score即final_score，设置过期时间如24小时，防止任务异常时旧数据无限期滞留）
5. 全局热门兜底单独计算，写入 hot:products

查询流程（RecommendService.guessYouLike，详见11-后端开发详细文档.md §6）：
优先读 Redis Sorted Set → 未命中读 recommend_result 表 → 仍无结果返回 hot:products
```

## 10. 算法评估方法（毕业论文"实验与分析"章节可直接依据）

### 10.1 离线评估

将 `user_behavior` 按时间切分为训练集（前 80% 时间段）与测试集（后 20% 时间段），用训练集计算推荐结果，与测试集中用户实际发生的行为做比对：

- **准确率（Precision@N）** = 推荐的 N 个商品中，测试集中用户真实交互过的商品数 / N；
- **召回率（Recall@N）** = 推荐命中的商品数 / 测试集中该用户实际交互的商品总数；
- **覆盖率（Coverage）** = 被推荐到的商品去重数 / 商品总数，用于评估是否存在"总是推荐少数热门商品"的问题。

### 10.2 在线评估（对应 `03-软件需求规格说明书.md` FR-S-10、FR-A-09）

- 需在推荐结果曝光处与用户点击处埋点（`recommend_result` 展示时记录曝光，点击时记录来源为推荐位）；
- **点击率 CTR** = 点击数 / 曝光数；**转化率** = 点击后下单数 / 点击数；
- 可选对比实验：为一部分用户展示纯热门排序（对照组），另一部分展示混合推荐结果（实验组），比较两组的 CTR/转化率差异，作为论文中"个性化推荐效果优于固定排序"的量化证据。

## 11. 数据规模假设与性能评估

毕业设计演示环境的数据规模假设（非生产环境）：

| 维度 | 假设规模 |
|---|---|
| 用户数 $m$ | 1,000 ~ 10,000（含测试脚本批量生成的模拟用户） |
| 商品数 $n$ | 500 ~ 5,000 |
| 单用户平均交互商品数 | 10 ~ 50 |

在该规模下，倒排索引优化后的相似度计算（§4.1/§5.1）可在数据库单机 + 应用内存中于数分钟内完成一轮全量计算，满足"每小时定时批量更新"的时效要求；Redis 中 `recommend:{userId}` 的 Sorted Set 单用户数据量约为 N×(8字节ID+8字节分值)，万级用户总占用在 MB 级别，内存开销可忽略，无需额外容量规划。
