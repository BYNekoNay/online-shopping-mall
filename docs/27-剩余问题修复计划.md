## 一、M-01 满赠促销（type=3）实现

### 1.1 规则定义（docs/10 §2.4.2 已明确，按此实现）

```json
// promotion.type=3 rule_json
{ "threshold": 150.00, "giftProductId": 5001, "giftSkuId": 50011, "giftQuantity": 1 }
```
- 商品金额（不含运费）≥ threshold → 赠送指定 SKU，赠品行 `is_gift=1, price=0`
- 赠品需预扣库存；**库存不足静默跳过赠送，不阻断下单**
- 赠品行随订单一并出库（支付时 DB 实扣）；不可单独售后/评价；统计按 is_gift=0 过滤

### 1.2 改动设计

| 文件 | 改动 | 说明 |
|---|---|---|
| `PromotionService` | 新增 `GiftInfo matchGift(Long shopId, BigDecimal goodsAmount)` | 在 matchActive(shopId) 中筛选 type=3 且 `goodsAmount >= threshold` 的促销，解析 ruleJson 返回 `GiftInfo(giftProductId, giftSkuId, giftQuantity)`；解析失败/不达标返回 null（容错 + 日志） |
| `OrderGroupProcessor.processGroup` | ① goodsAmount 计算完成后调用 matchGift ② 命中且 SKU 绑定校验通过（giftSkuId 属于 giftProductId，不符则跳过）③ 预扣赠品库存 `stockService.deduct(giftSkuId, giftQuantity)`，false/异常 → 跳过并 log.warn（不阻断下单）④ 预扣成功后构造赠品行追加到 `orderItems`（price=0、isGift=1、名称/图片取赠品商品快照）⑤ **注册事务同步 `afterCompletion(STATUS_ROLLED_BACK)` 归还赠品 Redis 库存**（事务回滚时自动归还，提交成功则保留——随订单出库）⑥ 购买行为记录循环**排除赠品行**（`isGift==1 continue`，防赠品污染推荐矩阵） | 核心落点；与现有 best-effort 模式一致 |
| `OrderService.review` | 评价入口校验：orderItemId 对应行 `isGift==1` 时拒绝（前端已不展示入口，后端兜底） | 与 docs/13"赠品不可评价"对齐 |
| `OrderEstimateController`（可选增强） | 估价返回命中满赠的赠品信息（供确认页展示"满赠：送XX"） | 不实现也不影响主流程，列为可选 |
| 测试 | `OrderGroupProcessorTest`/`PromotionServiceTest` 新增用例 | 见 §1.4 |

### 1.3 关键设计决策

1. **赠品行不参与金额计算**：追加到 orderItems 发生在 goodsAmount/freight/payAmount 计算完成后，赠品 price=0 → totalAmount/payAmount 天然不含赠品
2. **Redis 预扣与事务一致性**：用 `TransactionSynchronization.afterCompletion(STATUS_ROLLED_BACK)` 归还——事务回滚自动归还，提交成功保留（正确语义：赠品随订单出库）。避免"先扣 Redis、后插 DB、失败泄漏"问题
3. **支付链路自动覆盖**：pay() 遍历 orderItems 做 DB 实扣（含赠品行 `skuMapper.deductStock`）→ 赠品随订单出库 ✅；doCancel 遍历 items 归还（含赠品行）✅——无需改 pay/doCancel
4. **行为/统计口径**：购买行为排除赠品（防推荐污染）；统计已按 is_gift=0 过滤（第一级确认）✅
5. **前端零改动**：BatchPay.vue / Detail.vue / List.vue 的 `isGift → 赠品标签` 渲染已就绪（修复时预留）

### 1.4 验证用例（新增）

| 用例 | 断言 |
|---|---|
| 满赠达标：goodsAmount ≥ threshold | 订单含赠品行（isGift=1、price=0、qty=giftQuantity），payAmount 不含赠品 |
| 满赠不达标 | 无赠品行 |
| 赠品库存不足 | 下单成功但无赠品行（静默跳过 + 日志），其余商品正常 |
| 赠品 SKU 绑定错误（giftSkuId 不属于 giftProductId） | 跳过赠送，不阻断 |
| 赠品参与行为埋点排除 | 购买行为不含赠品 productId |
| 事务回滚（如券核销失败） | 赠品 Redis 库存自动归还（afterCompletion） |

## 二、L2-02 doCancel 在 DB 事务内执行 Redis 库存归还

### 2.1 现状与问题

- `cancelOrder`/`cancelOrderBySystem` 标注 @Transactional → `doCancel`：
  ① DB 原子更新 status 0→5 → ② 查 items → ③ **Redis rollback（事务内）** → ④ DB 券释放 → ⑤ DB 积分返还
- 若 ④/⑤ 抛异常 → 事务回滚（status 回 0）→ 但 ③ Redis 库存已归还 → **可售库存虚增**（订单仍待付款但库存已被"归还"，超卖风险）

### 2.2 修复方案（方案 A：afterCommit 回调，最小改动）

| 文件 | 改动 |
|---|---|
| `OrderService.doCancel` | 不再在事务内直接执行 Redis 归还：收集 items 的归还清单（skuId→qty / productId→qty）→ 注册 `TransactionSynchronization.afterCommit` 回调，**事务提交成功后**执行 `stockService.rollback/rollbackProduct`；回调内 catch 记录失败日志（漏还补偿：warn + 清单，可人工对账） |
| 其余 | ① DB 状态更新 ② 券释放 ③ 积分返还保持事务内（与状态原子性一致，不拆） |

**效果**：
- 事务回滚 → afterCommit 不执行 → Redis 不归还 → 一致性 ✅
- 事务提交 → afterCommit 归还 → 正常 ✅
- 与现有支付幂等标记的 afterCommit 模式（C1 修复）一致，风格统一

**已知残留风险**（记录）：提交成功后 Redis 归还失败（Redis 抖动）→ 库存漏还，靠日志 + 人工对账；概率极低。彻底方案（outbox/本地消息）超出毕设范围，记录为架构优化项。

### 2.3 验证用例

| 用例 | 断言 |
|---|---|
| 取消订单（正常路径） | 事务提交后 Redis 归还被调用（mock 校验） |
| 取消订单（券释放抛异常） | 事务回滚，Redis 归还**不被调用** |
| 超时任务取消 | 同上（cancelOrderBySystem 同路径） |

### 2.4 预估工作量：约 1.5~2h（含测试重构）

## 四、风险与取舍

| 项 | 说明 |
|---|---|
| 满赠多档/多赠品 | ruleJson 为单档单赠品（docs/10 定义如此），多档不支持（毕业设计范围） |
| 赠品与券叠加 | 赠品不参与金额计算，天然不与满减/折扣/券冲突 |
| 赠品 SKU 已删除 | 查询为 null → 跳过赠送（best-effort），不阻断 |
| afterCommit/afterCompletion 内 Redis 失败 | 日志 + 人工对账（概率极低） |
